## 1. 架构总览

### 1.1 分层与依赖方向

```
                    ┌──────────────────────────────────────┐
   浏览器  ────────► │  frontend/src  (Vue 3 SPA)           │
                    │  features/  ← 按角色分目录            │
                    │      ↓ 只经过 services/api.ts         │
                    │  services/  (api / labels / csv / …)  │
                    └───────────────┬──────────────────────┘
                                    │ HTTP  /api/v1/**
                                    │ 统一封装 {success,data,request_id,error}
                    ┌───────────────▼──────────────────────┐
                    │  backend/app/api/v1/   ← 只做三件事：  │
                    │    路由 · 参数校验(Pydantic) · 权限注入 │
                    │    （不写业务逻辑，不直接拼复杂查询）    │
                    └───────────────┬──────────────────────┘
                                    │ 函数调用（同进程）
                    ┌───────────────▼──────────────────────┐
                    │  backend/app/services/  ← 业务逻辑全在这 │
                    │  评分 · 任务 · 关怀 · 统计 · 导入 · 导出 │
                    └───────────────┬──────────────────────┘
                                    │ SQLAlchemy ORM
                    ┌───────────────▼──────────────────────┐
                    │  backend/app/models/  ← 表结构声明       │
                    └───────────────┬──────────────────────┘
                                    │ PyMySQL
                    ┌───────────────▼──────────────────────┐
                    │           MySQL 8.0 / 8.4            │
                    └──────────────────────────────────────┘

      横切（被上面各层依赖，自己谁也不依赖）：
        core/      config · errors(统一响应) · …
        security/  tokens · passwords · permissions · data_scope
        schemas/   Pydantic 出入参模型
```

依赖方向是**单向**的，四条硬规矩：

| 规矩 | 理由 |
|---|---|
| `api/v1/` 不写业务逻辑 | 同一段逻辑被两个端点复用时，写在 api 层必然要复制一份 |
| `services/` 不 import `fastapi` | 服务层必须能在 pytest 里直接调用，不需要构造 Request |
| `models/` 不 import `services/` | ORM 声明是叶子，被所有层读 |
| `scale_engine/engine.py` **不碰数据库** | 见 §4，纯函数是"评分可复算"的前提 |

**唯一一处刻意的例外**是 `scale_engine/engine.py`：它是一个纯函数模块，
输入是"题目配置 + 答案字典"，输出是一个 `ScaleCalculation` 数据类，
既不 import `Session` 也不 import `models`。代价是调用方（`assessment_service`）
要做一次"把数据库行转成引擎输入"的适配；收益是这个 348 行的模块
可以用一份 JSON 夹具完整地单元测试（`test_scale_engine.py`），
且"同一次答题在不同时间复算得到同一个结果"这件事在结构上成立。

### 1.2 运行时拓扑（三种部署形态，各自完整）

系统有**三条互不替换的部署路径**，它们共享同一份代码，差别在"谁发前端"与"谁负责起停"：

| | 开发 | Docker Compose | 单机 / 局域网一键安装 |
|---|---|---|---|
| 前端 | Vite dev server `:5173` | nginx 容器 `:80` | 后端进程自己发（`XLP_WEB_DIR`）或内置静态服务器 |
| 后端 | uvicorn `:8000`（`--reload`） | uvicorn 容器 `:8000` | uvicorn `:8000`（可见控制台窗口 / 计划任务） |
| 数据库 | 本机 MySQL | mysql:8 容器（`root/root`） | 目标机已装的 MySQL 8.0 Server |
| 跨域 | Vite proxy `/api → 127.0.0.1:8000` + 后端 CORS | 不跨域（nginx 同源反代） | **不跨域**（同源是硬要求，见下） |
| 起停 | 手工 `make dev` | `docker compose up` | 双击「启动服务.bat」/ 开机计划任务 |

**同源是一条硬约束，不是偏好。** `services/api.ts` 里
`const API_BASE = '/api/v1'` 是相对路径，且 `createWebHistory()` 没带 base。
所以生产环境只有两种成立方式：① 一个进程同时发 API 与页面（一键安装走这条）；
② 中间放一个会反代 `/api` 的 nginx（Docker 那条）。**没有第三种。**
用 `python -m http.server` 单独发 `frontend/dist` 的后果是：
登录页打得开，**每一次登录都失败**（`POST /api/v1/auth/login` 拿到的是那个静态服务器的
404 HTML，前端解析时报 `Unexpected token '<'`），而那个窗口自己看起来一切正常。
`deploy/windows/serve_frontend.py` 存在的唯一理由就是补上这个反代。

### 1.3 一次典型的读请求（含权限与审计）

以"心理老师打开一名学生的关怀档案详情"为例，`GET /api/v1/care-cases/{student_id}`：

```
1. AppLayout 已经在启动时 GET /auth/me，拿到 role / scopes / must_change_password
2. api.ts 带 Authorization: Bearer <jwt>
3. FastAPI 路由依赖链（api/v1/care.py）：
     get_current_user          → 解 JWT → 查 user_account → 校验 active
     require_capability(STUDENT_PSYCH_DETAIL, allow={SCOPED})
                               → 查 role_permission → 缺行回退 CAPABILITY_DEFAULTS
4. care_service.get_care_case(db, user, student_id)：
     ensure_student_in_scope(db, user, student_id)
                               → 学生不存在 404 / 不在范围 403
                               → 内部复用 student_scope_predicate（同一个定义）
     取该学生 id 最大的档案（**不过滤 CLOSED**）
5. audit_service.write(...)     ← 在返回数据之前写
     action="查看学生档案" resource_type="STUDENT_CARE_CASE" student_id=…
6. api 层套 ok(data) → {success:true,data:{…},request_id,error:null}
```

第 4 步与第 5 步的次序是**约定**（`CLAUDE.md` §8）：敏感读取**先写审计，后返回数据**。
被拒绝的读取（第 4 步抛 403）**不写审计**——给一次被拒的读取记上"查看档案"，
会让访问轨迹反过来撒谎。

## 2. 技术选型与理由

### 2.1 后端

| 选型 | 版本 | 为什么 |
|---|---|---|
| FastAPI | ≥0.115 | 依赖注入天然适配"能力矩阵 + 数据范围"这种每个端点都要过一遍的守卫；Pydantic 出入参校验省掉一整层手写校验 |
| SQLAlchemy 2.0 | ≥2.0 | `Mapped[...]` 声明式 + `select()` 2.0 风格，类型可被 mypy/IDE 理解；`student_scope_predicate` 返回 `ColumnElement[bool]` 直接进 `WHERE` |
| Alembic | ≥1.13 | 迁移与 ORM 声明分离，是"生产库结构由迁移建、测试库结构由 metadata 建"这条双轨制的前提 |
| PyMySQL | ≥1.1 | 纯 Python，不需要编译；`cryptography` 是 MySQL 8 默认认证插件 `caching_sha2_password` 的**前提**（见 §8） |
| PyJWT | ≥2.8 | 无状态令牌 |
| bcrypt | ≥4.1 | 口令哈希。**不用 passlib**——passlib 已停止维护，且它对新版 bcrypt 的版本探测会抛警告 |
| pydantic-settings | ≥2.4 | `.env` + 环境变量 + 默认值三层，`XLP_` 前缀避免与系统变量撞名 |
| uvicorn[standard] | ≥0.30 | ASGI 服务器 |

**没有引入的东西与理由：**

- **没有 Celery / 消息队列。** 全站唯一的"后台任务"是导入与导出，两者都是
  同步的、秒级的（一份两百行的 CSV），引入队列会把"导入失败"从一句 422
  变成"提交成功但结果要看另一个地方"。
- **没有 Redis。** 没有需要跨进程共享的状态：防抖在前端、排序分页在 SQL、
  唯一性在数据库约束。
- **没有 ORM 之外的 SQL 生成器。** 统计那部分手写 `select()` 反而更短。

### 2.2 前端

| 选型 | 版本 | 为什么 |
|---|---|---|
| Vue 3.5 | `<script setup>` + `ref`/`computed` | 一个 20 个路由的中型 SPA，组合式 API 够用 |
| TypeScript 5.6 | `vue-tsc -b` 进构建 | `api.ts` 里的响应类型是"接口契约"的前端镜像，类型错了构建就红 |
| Vite 6 | 构建 + dev server | 冷启动快；`server.proxy` 一条配置解决跨域 |
| vue-router 4 | `createWebHistory()` | 深链与 F5 靠后端 catch-all 兜住 |

**刻意不引入的：**

| 没引入 | 用什么替代 | 理由 |
|---|---|---|
| **Pinia / Vuex** | 模块级单例 `composables/useSettings.ts` + 组件局部状态 | 全站唯一的跨页共享状态是"系统配置"（校名、品牌名、关怀室信息）。一份模块级 `ref` 就够，引入状态库会带来"这份状态什么时候该重置"的新问题。其余数据都是"进这一页拉一次" |
| **Element Plus / Ant Design Vue** | 13 个自写组件（`Modal` / `DataTable` / `FormDialog` / `Toast` / …） | 全站样式只有一份 `assets/styles.css`（约 500 行）。引入 UI 库会让"设计系统"从一份 CSS 变成"库的默认值 + 我们的覆盖"，而 §7.5 的无障碍契约需要逐个组件钉住，自写反而更可控 |
| **ECharts / Chart.js** | `TrendChart.vue`（179 行 SVG）+ `DimensionRadar.vue`（112 行 SVG） | 需要的是折线、雷达、条形三种，都是纯 `<svg>` 能画完的。引入图表库会把 bundle 从 ~200KB 推到 ~1MB，而目标机是学校内网 |
| **axios** | 手写 `fetch` 封装（`services/api.ts`，1315 行） | 1315 行里 1200 行是接口函数与类型，请求部分只有 60 行。axios 的拦截器/取消令牌在这里没有使用场景 |
| **Vitest / Jest** | Playwright e2e | 见 §9：组件测试能证明"函数返回了什么"，证不了"屏幕上写了什么"，而本项目的回归 90% 发生在"屏幕上写了什么"那一层 |
| **ESLint / Prettier** | `vue-tsc` 类型检查 | 见 §10 技术债 T-06 |

### 3.2 统一响应封装

`core/errors.py` 全文只有 42 行，但它是全站**唯一**的响应形状来源：

```python
@dataclass
class AppError(Exception):
    code: str
    message: str
    status_code: int = 400

def ok(data=None, request_id_value=None):
    return {"success": True, "data": data if data is not None else {},
            "request_id": ..., "error": None}

def error_response(code, message, status_code, request_id_value=None):
    return JSONResponse(status_code=status_code, content={
        "success": False, "data": None,
        "request_id": ..., "error": {"code": code, "message": message}})

async def app_error_handler(_, exc: AppError):
    return error_response(exc.code, exc.message, exc.status_code)
```

三条后果，每一条都有实现上的分量：

**① `data` 为 `None` 时被替换成 `{}` 而不是 `null`。**
前端 `api.ts` 统一 `body.data`，`null` 会让 `Object.keys()` 之类炸掉。

**② 前端拿不到 HTTP 状态码。** `apiRequest` 里是
`const body = await response.json(); if (!body.success) throw new Error(body.error?.message)`。
它**不读 `response.status`**，所以 401 与 500 在前端长得一样。

**但"服务端答了话"与"一个字都没收到"是分得开的**（2026-09-17 补）：

| 情形 | 抛什么 | 前端判据 |
|---|---|---|
| 后端没起来 / 网断 / 跨域被拒 | `TypeError` | `err instanceof TypeError` |
| 响应体不是 JSON（网关 HTML 错误页） | `SyntaxError` | 同上判据 |
| 服务端按统一封装答了错 | `Error`，`err.message` = `error.message` | 其余 |

登录页据此写 `loginFailureMessage()`：在此之前它把**一切**失败都报成
"账号、角色或密码不正确"，于是"后端没起来"和"密码打错了"在屏幕上长得一样，
用户会一直重打密码，而问题在别处。服务端 401 的原文一字未改——
变的只是 500 一类的故障第一次有机会说出自己的名字。

**③ `RequestValidationError` 被统一成 `VALIDATION_ERROR` / 422。**
FastAPI 默认返回的是一份带 `loc`/`type`/`ctx` 的数组，前端要显示它得先写一个解析器。
统一之后前端只需要读一句话（代价是丢了字段级定位，但本项目的表单都是
单字段提交，字段级定位的价值不大）。

**错误码全集**（14 个，从代码里 grep 出来的实际使用集合）：

| 码 | 含义 | 典型状态码 |
|---|---|---|
| `VALIDATION_ERROR` | 参数/业务校验失败（用得最多，46 处） | 422 / 400 |
| `NOT_FOUND` | 对象不存在 | 404 |
| `ROLE_FORBIDDEN` | 角色无权（能力矩阵拒绝） | 403 |
| `SCOPE_FORBIDDEN` | 角色有权但**这名学生**不在其数据范围内 | 403 |
| `AUTH_REQUIRED` | 未登录 / token 失效 / 账号被停用 | 401 |
| `AUTH_INVALID` | 账号密码不匹配 | 401 |
| `ACCOUNT_LOCKED` | 连续失败超阈值，账号暂时锁定 | 403 |
| `SESSION_LOCKED` | 答卷已提交，不可再改 | 409 |
| `SCALE_INVALID` | 量表规则/题目配置不合法 | 422 |
| `PURPOSE_REQUIRED` | 敏感读取/导出缺少用途参数 | 422 |
| `MASK_FORBIDDEN` | 请求解除姓名遮蔽但缺少 `STUDENT_PSYCH_DETAIL: SCOPED` | 403 |
| `ANSWERS_INCOMPLETE` | 交卷时未答满 | 422 |
| `ANSWER_INVALID` | 选项值不在允许集合内 | 422 |
| `IDEMPOTENCY_CONFLICT` | 同一幂等键的重复提交 | 409 |

**`ROLE_FORBIDDEN` 与 `SCOPE_FORBIDDEN` 是两个不同的词**，这条区分是刻意的：
前者说"你这个角色就不该做这件事"，后者说"你能做这件事，但这位学生不归你管"。
前端对两者的处置也是分开的——前者通常是导航不该出现，后者通常是一条提示。

### 3.3 配置系统

`core/config.py` 全文 33 行：

```python
class Settings(BaseSettings):
    app_name: str = "心晴心理测评与关怀平台"
    api_prefix: str = "/api/v1"
    database_url: str = "mysql+pymysql://root:password@127.0.0.1:3306/xinliceping"
    jwt_secret: str = "dev-only-change-me-dev-only-change-me"
    jwt_algorithm: str = "HS256"
    access_token_expire_minutes: int = 120
    password_lock_threshold: int = 5
    password_lock_minutes: int = 30

    host: str = "127.0.0.1"
    port: int = 8000
    web_dir: str = ""
    log_dir: str = ""
    log_level: str = "INFO"
    docs_enabled: bool = True

    model_config = SettingsConfigDict(env_file=".env", env_prefix="XLP_")

@lru_cache
def get_settings() -> Settings: return Settings()
```

**`web_dir` 的默认值是空串，等于"这个功能不存在"。**
`main._mount_web()` 第一行 `if not settings.web_dir: return`，
所以开发（前端在 5173）、pytest、e2e 的行为**一字不变**。
新能力默认关闭，是这类改动的标准做法。

**`docs_enabled` 默认 `True`，安装脚本写 `0` 关掉它。**
`/docs`、`/redoc`、`/openapi.json` 三个要么一起开要么一起关——
只关 `/docs` 而留着 `/openapi.json` 等于没关，那份 schema 就是全部内容。
为什么生产要关：那一整个网段的人都拉得到整份接口形状（含权限依赖的名字与参数）。

**`.env` 是 CWD 相对的**，`SettingsConfigDict(env_file=".env")` 与
`alembic.ini` 的 `script_location = alembic` 都相对当前工作目录，
**而 `.env` 缺失是被静默跳过的**（pydantic-settings 的默认行为）。
计划任务配错工作目录的后果因此不是报错，是"用全默认值跑起来"——
连的是 `root:password@localhost`，与操作员填的那一份毫无关系。
`run_server.py` 进门就 `os.chdir` 到仓库根，让这件事不依赖任务配置。

**配置的"两个家"要分清**（这是一个反复踩过的坑）：

| 家 | 谁写的 | 界面上出现过吗 |
|---|---|---|
| `school.name`（表） | `db/seed.py`、学生导入 | **从来没有** |
| `system_setting` 的 `org.school_name` | 管理员在「账号与权限 → 系统配置 → 机构标识」里改 | 登录页、顶栏，以及用户改的那一格 |

用户报过："添加账号时，数据范围还显示了青禾实验学校，与我在配置中写的第十三中学不匹配"。
根因是 `auth_service.scope_options` / `resolve_scope_names` 读的是 `school.name`，
而那是全站**唯一**渲染它的地方。现在两处都走 `_school_display_names`（读配置，
读不到才回落 `school.name`）。**没有**把配置值写回 `school.name`——
那一行由种子/导入维护，界面上没有编辑它的入口，写回去等于让一个只读列去追一个可写配置。

### 3.4 数据库会话与事务边界

`db/session.py` 19 行：

```python
engine = create_engine(get_settings().database_url, pool_pre_ping=True)
SessionLocal = sessionmaker(bind=engine, autoflush=False, autocommit=False,
                            expire_on_commit=False)

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

四个参数各有分量：

| 参数 | 值 | 理由 |
|---|---|---|
| `pool_pre_ping` | `True` | MySQL 会掐掉空闲连接（`wait_timeout` 默认 8 小时），学校场景下"早上第一请求"必然撞上。pre-ping 花一次 RTT 换掉一个无法复现的 `OperationalError` |
| `autoflush` | `False` | 显式 flush。否则一条中间态的查询会意外把半写好的对象刷进去 |
| `autocommit` | `False` | 事务边界由服务层显式 `commit()` 控制 |
| `expire_on_commit` | `False` | 提交后对象仍可读。序列化通常在 `commit()` 之后，开着它会触发一批本可避免的 SELECT（或在 session 关闭后抛 `DetachedInstanceError`） |

**事务边界在服务层**，典型形状是：

```python
def some_service(db, user, payload):
    ...                               # 校验
    row = Model(...); db.add(row)
    db.flush()                        # 拿到 id，但还没提交
    audit_service.write(db, ...)      # 审计与业务在同一个事务里
    db.commit()
    return row
```

"审计与业务同一个事务"是刻意的：一次成功的写操作与它的轨迹要么都在，要么都不在。
审计行**不参与** `db.flush()` 之外的任何耦合——它没有指向业务行的外键。

`conftest.py` 里测试用的 session 参数不同（`expire_on_commit=False` 相同，
但用 `StaticPool` + 内存 sqlite），见 §9。

### 3.5 认证与鉴权

#### 3.5.1 JWT

```python
def create_access_token(user_id: int, role: str) -> str:
    expire_at = datetime.now(UTC) + timedelta(minutes=settings.access_token_expire_minutes)
    payload = {"sub": str(user_id), "role": role, "exp": expire_at}
    return jwt.encode(payload, settings.jwt_secret, algorithm=settings.jwt_algorithm)
```

- `sub` 是 **`str`**——PyJWT 对 `sub` 有类型要求（RFC 7519 规定是 StringOrURI），
  传 `int` 会在某些版本上抛异常。
- payload 里**没有** `scope` / `permissions`。权限**每个请求现查**：
  `get_current_user` 查一次 `active`，`require_capability` 查一次 `role_permission`。
  代价是每个请求多 1–2 次 SELECT（都有主键/唯一索引），
  收益是"改了权限立刻生效"与"停用立刻生效"这两件事不需要任何失效机制。
- `decode_access_token` 把 `PyJWTError` 统一转成 `AppError("AUTH_REQUIRED", "请先登录", 401)`，
  所以过期、签名错、格式错对客户端是同一件事。

#### 3.5.2 每一个请求都查 `active`

```python
def get_current_user(token, db) -> UserAccount:
    payload = decode_access_token(token)
    user = db.get(UserAccount, int(payload["sub"])) if payload.get("sub") else None
    if not user or not user.active:
        raise AppError("AUTH_REQUIRED", "请先登录", 401)
    return user
```

**停用不需要等 token 过期**——这是"没有删除接口"这条设计的直接后果：
`audit_logs` / `manual_review` / `follow_up_record` 都指着 `user_account`，
删一行会把这些全部悬空（库里没有 `ondelete=`）。停用够用，正因为每个请求都查一次。
`test_account_admin_api.py` 里那条"停用后下一次请求就 401"钉住它。

#### 3.5.3 登录失败锁定

`authenticate` 的行为（`auth_service.py`）：

```
账号不存在          → AUTH_INVALID（**不写 failed_attempts**——没有行可写，也不该为
                       一个不存在的账号创建行）
账号存在、口令错    → failed_attempts += 1；达到 password_lock_threshold(5)
                      → 写 locked_until = now + password_lock_minutes(30)
                      → 回 ACCOUNT_LOCKED
账号锁定期内        → ACCOUNT_LOCKED（**不再累加**——已经锁了，再累加只是噪声）
口令正确但 active=False → AUTH_REQUIRED（与未登录同一句话，不泄漏"这个账号存在"）
口令正确且 active   → 清 failed_attempts / locked_until，写 last_login_at，发 token
```

**重置密码顺手解锁**：`auth_service.reset_password` 清掉
`failed_attempts` / `locked_until`。这样"被锁住的账号不用等"——
管理员（或磁盘上那个「重置管理员密码.bat」）重设一次密码就是解锁。

#### 3.5.4 口令哈希

`security/passwords.py` 10 行，bcrypt 直调：

```python
def hash_password(p): return bcrypt.hashpw(p.encode("utf-8"), bcrypt.gensalt()).decode("utf-8")
def verify_password(p, h): return bcrypt.checkpw(p.encode("utf-8"), h.encode("utf-8"))
```

`password_hash` 列宽 255（bcrypt 输出固定 60 字符，留足余量以便将来换算法）。

### 3.6 能力矩阵（`security/permissions.py`）

**五个能力 × 四个角色**，实现在 253 行的 `permissions.py` 里。

#### 3.6.1 默认矩阵（`CAPABILITY_DEFAULTS`）

| 能力 | counselor | leader | admin | student |
|---|---|---|---|---|
| `AGGREGATE_STATS` 聚合统计 | `SCOPED` | `SCHOOL` | `NONE` | `NONE` |
| `STUDENT_PSYCH_DETAIL` 学生心理详情 | `SCOPED` | `SUMMARY` | `NONE` | `NONE` |
| `KEY_QUESTIONS` 重点题/原始答卷 | `GRANTED_WITH_AUDIT` | `NONE` | `NONE` | `NONE` |
| `ORG_ACCOUNT` 组织与账号 | `READ_BASIC` | `READ_SUMMARY` | `MANAGE` | `OWN` |
| `CONTROLLED_EXPORT` 受控导出 | `PSYCH_SUMMARY` | `PROGRESS_SUMMARY` | `BASE_ONLY` | `NONE` |

`CAPABILITY_DEFAULTS` **镜像了能力层出现之前代码已经执行的规则**，
所以 `role_permission` 表为空时行为与硬编码时代完全一致——
既有测试就是这件事的回归网。

#### 3.6.2 每个能力的合法等级（`CAPABILITY_LEVELS`）

这五个列表是那 12 个等级的**真正定义域**，**从紧到松**排列：

```python
CAPABILITY_LEVELS = {
    AGGREGATE_STATS:      [NONE, SCOPED, SCHOOL],
    STUDENT_PSYCH_DETAIL: [NONE, SUMMARY, SCOPED],
    KEY_QUESTIONS:        [NONE, GRANTED_WITH_AUDIT],
    ORG_ACCOUNT:          [NONE, OWN, READ_SUMMARY, READ_BASIC, MANAGE],
    CONTROLLED_EXPORT:    [NONE, BASE_ONLY, PROGRESS_SUMMARY, PSYCH_SUMMARY],
}
```

**为什么需要这张表**（2026-09-17 加）：在此之前权限弹窗给 20 个格子里的**每一个**
都列出全部 12 个等级，于是 `student/ORG_ACCOUNT = 管理`、
`leader/KEY_QUESTIONS = 授权范围` 这类组合都是可选且可存的——存进去不报错，
只是永远不会被任何端点认出来（`scope_allows` 是纯集合成员判断，
没有端点把 `MANAGE` 放进 `ORG_ACCOUNT` 的 allow 集里给一个学生）。
一个能保存却没有任何效果的选项，读者只会得出"这东西坏了"的结论。

顺序还有第二个用处：前端比对"比默认更宽"时靠的是**下标**，不是另写一张宽松度表——
两张表迟早会各说各话。

`test_permissions.py` 把守"两张表一致"：`CAPABILITY_DEFAULTS` 里的每个能力键
都必须在 `CAPABILITY_LEVELS` 里有定义。

#### 3.6.3 每格"选了会怎样"（`LEVEL_DESCRIPTIONS`）

按能力分别写，因为**同一串等级名在不同能力下意思不同**：

- `SCOPED` 在 `AGGREGATE_STATS` 里是"只算我管的学生"，在 `STUDENT_PSYCH_DETAIL` 里是"能打开档案正文"；
- `SUMMARY` 在 `STUDENT_PSYCH_DETAIL` 里恰好是**不能**开档案的那一档。

写一份全局释义会把这两件事说成一件。这 15 条中文（5 能力 × 各自等级数）
直接渲染进权限弹层的下拉框。

#### 3.6.4 fail-safe 回退

```python
def resolve_scope(db, role_code, capability_key) -> str:
    try:
        row = db.scalar(select(RolePermission).where(...))
    except SQLAlchemyError:
        row = None                     # 读不到就当成"没配过"
    if row is not None:
        return row.scope_level
    return CAPABILITY_DEFAULTS.get(capability_key, {}).get(role_code, NONE)
```

**表空、缺记录、或查询抛 `SQLAlchemyError` 时一律回退默认矩阵**，
绝不 fail-open 成"全部允许"。注意回退的目标**不是 `NONE`** 而是 `CAPABILITY_DEFAULTS`
——回退成 `NONE` 会让一次数据库抖动把所有心理老师锁在门外。

#### 3.6.5 `allow` 参数：描述性等级不可互换

```python
def scope_allows(db, role_code, capability_key, allow: set[str] | None = None) -> bool:
    scope = resolve_scope(db, role_code, capability_key)
    if scope == NONE:
        return False
    return allow is None or scope in allow

def require_capability(capability_key, allow=None):
    def checker(current_user=Depends(get_current_user), db=Depends(get_db)):
        if not scope_allows(db, current_user.role_code, capability_key, allow):
            raise AppError("ROLE_FORBIDDEN", "当前角色无权执行该操作", 403)
        return current_user
    return checker
```

`allow=None` 接受所有非 `NONE`；**暴露明细的端点必须显式传 `allow`**。
`api/v1/care.py` 里的档案详情传 `allow={SCOPED}`——
不传的话 admin 的 `BASE_ONLY`（在别的能力上）与 leader 的 `SUMMARY`
会被静默提升成"能看档案正文"。

**同一条规矩的另一处：导出解除姓名遮蔽也要 `STUDENT_PSYCH_DETAIL: SCOPED`。**
德育领导的 `CONTROLLED_EXPORT` 是 `PROGRESS_SUMMARY`，
它在 `GET /students` 上连按行姓名都拿不到，却能靠 `{"mask_names": false}`
导出一份实名名单——受控导出不能成为绕过心理详情的旁路。
**角色能导出摘要不代表它能导出实名明细。**

#### 3.6.6 `GET /students/results` 的双门槛

2026-09-17 加，是 §3.6.5 的**镜像**：

```
STUDENT_PSYCH_DETAIL: {SCOPED}   且   ORG_ACCOUNT: {MANAGE, READ_BASIC}
```

响应里同时有**身份列**（学号/姓名/年级/班级，归组织与账号）与
**等级列**（关注等级/总分，归心理详情）。既然受控导出不得成为心理详情的旁路，
**心理详情同样不得成为读组织名册的旁路**。

拦住的是谁：德育领导（名册是 `READ_SUMMARY`、心理详情是 `SUMMARY`）与
系统管理员（有 `ORG_ACCOUNT: MANAGE`、没有心理详情）。

比同一页上的 `GET /care-cases`（只查 `STUDENT_PSYCH_DETAIL: SCOPED`）严一档，
这是**有意的**：`care-cases` 给的是已经开档的那批学生，而这一个给的是整份名册。

该能力在**两处**各查一次（`students.py` 的路由依赖 +
`analytics_service.ensure_student_result_reader`，与 `care.py` / `care_service`
的既有形状一致），所以单独拆掉任何一处都不会让测试变红——**两处一起拆才会**。
别把"拆了一处仍然全绿"读成守卫失效。

#### 3.6.7 测评任务不是能力，是角色

2026-09-17 裁决：测评任务是学校业务而不是系统级配置，
所以**系统管理员读写都不包含它**——写归心理老师（业务闭环的负责人），
读归心理老师 + 德育领导。这两条用 `require_role` 而不是 `require_capability`。

连带改动：`create_school_assessment_task` 发放目标行时按**创建者的数据范围**过滤。
写权还在管理员手上时"发给全体在读学生"与"发给管辖的全体"是同一件事，
所以那条谓词缺失了很久没有任何东西能发现它。

#### 3.6.8 自锁防护

- 系统管理员不能移除自身的「组织与账号」权限；
- 管理员不能停用自己的账号（"停用之后就没人能再进入这一页了"）。

后者排在**服务端**而不只是界面上。

### 3.7 数据范围（`security/data_scope.py`）

能力回答"心理老师能不能看个案详情"，**范围**回答"这位心理老师能不能看**这名**学生"。
两者互补，缺一个就漏一种洞。

#### 3.7.1 两个入口，一个定义

| 入口 | 用在 | 语义 |
|---|---|---|
| `ensure_student_in_scope(db, user, student_id)` | 客户端传来的 ID | 取到之后校验。否则**档案 ID 本身就成了越权凭据** |
| `student_scope_predicate(db, user)` | 列表 / 聚合查询 | 加进 `WHERE`，把结果集收缩到用户范围 |

```python
def student_scope_predicate(db, user) -> ColumnElement[bool]:
    try:
        scopes = db.scalars(select(UserScope).where(UserScope.user_id == user.id)).all()
    except SQLAlchemyError:
        return false()
    clauses = []
    for scope in scopes:
        if scope.scope_type == ScopeType.SCHOOL and scope.school_id is not None:
            clauses.append(Student.school_id == scope.school_id)
        elif scope.scope_type == ScopeType.GRADE and scope.grade_id is not None:
            clauses.append(Student.grade_id == scope.grade_id)
        elif scope.scope_type == ScopeType.CLASS and scope.class_id is not None:
            clauses.append(Student.class_id == scope.class_id)
        elif scope.scope_type == ScopeType.STUDENT and scope.student_id is not None:
            clauses.append(Student.id == scope.student_id)
    if not clauses:
        return false()
    return or_(*clauses)


def student_in_scope(db, user, student) -> bool:
    return db.scalar(
        select(Student.id).where(Student.id == student.id, student_scope_predicate(db, user))
    ) is not None
```

**三个必须理解的细节：**

**① 谓词绝不返回 `None`。** scope 表读不到、或用户没有 scope 行 → **恒假谓词**。
返回 `None` 会让调用方读成"不用过滤"而 fail-open，那是这一层唯一不能出现的结果。

**② `is not None` 判断是必要的，不是防御性编程。** 一个 `GRADE` 类型但 `grade_id` 为 NULL
的半填行，与一个 `grade_id` 也为 NULL 的学生，在 SQL 里 `NULL = NULL` 结果是 `UNKNOWN`
（不是 `TRUE`），所以本来也不会匹配——但写成 `Student.grade_id == scope.grade_id`
在 ORM 里会被翻译成 `IS NULL` 比较（SQLAlchemy 的 `==` 对 `None` 有特殊处理），
那就真的匹配上了。这两个 `is not None` 是**半填的行不得授予一切**这条的唯一防线。

**③ `student_in_scope` 建立在谓词之上**，所以守卫与过滤器**不可能各说各话**——
列表里出现的学生，个案接口一定也接受。代价是每次多一条 SELECT，值得。

#### 3.7.2 拒绝时**不写审计**

给一次被拒的读取记上"查看重点题"，会让访问轨迹反过来撒谎。
所以 `ensure_student_in_scope` 抛 403 时，调用方（`care.py` 等）不会走到写审计那一步。

#### 3.7.3 谓词覆盖到哪

`care_service`、`analytics_service`、`task_service`、`export_service`、
`api/v1/students.py`、`api/v1/audit.py` 的列表与聚合都过 `student_scope_predicate`。

**两处刻意不过滤：**

- `analytics_service.leader_progress` —— 能力要求 `SCHOOL`，德育领导本就该看全校，改了反而错；
- `care_service.list_assignable_owners` —— 返回的是心理老师名单，不是学生数据。

**以及一个口径盲点：** `audit_logs.student_id` 可空，规则是
**命名了学生的行按范围过滤，未命名学生的组织级事件（登录 / 导出 / 导入）保留**。

#### 3.7.4 范围的口径要写进界面

"全部学生"这四个字会把人带向"全校"——一个只带 1 个班范围的心理老师
会以为这所学校只有 40 个学生。它现在在页头写「范围：全校 / 你负责的班级 …」，
依据是 `/auth/me` 的 `scopes[]`（`CurrentUser.scopes` 2026-09-17 才补上类型——
**那一列一直在响应里，只是此前 `api.ts` 没有类型所以没有读者**）。

多行范围由 `student_scope_predicate` 用 `or_` 合并，所以界面上是并列（并集）；
取不到 `scopes` 时**整句不出现**，不猜一个"全校"。

**聚合数字的口径跟角色走**：`SCOPED`（心理老师）的比率描述他自己的授权范围，
`SCHOOL`（德育领导）的描述全校——这正是能力词汇表里已有的区分。
范围数字必须在 UI 上写明口径，否则它冒充全校数字，比不给数字更糟。

#### 3.7.5 员工范围行只有一个写入方

2026-09-17 补：`auth_service.create_account` 与 `update_account`。
在那之前 `user_scope` 里员工那几行只由 `db/seed.py` 写，
所以"范围配错了"在界面上没有任何出路——而这正是这一层的输入。

两条约定：

- `update_account` 换范围是**整段替换**（`_scope_signature` 比对，一样就不动，
  于是重发同一个范围既不写审计也不换行 id）。**追加**会让一个账号越改越宽，
  而宽出来的那一段在界面上一行一个字列着，很容易读成"新配的那一段"。
- 范围行是**叶子表**（没有任何东西引用 `user_scope`），所以删了重插是安全的。
  其余每一张表的外键都是 RESTRICT 且没有 `ondelete=`（§5.4），**别把这条结论推广出去。**

**数据范围是必填的，不是选填的。** 谓词在"用户没有 scope 行"时恒假，
所以一个没有范围的员工账号登录得进来、每个列表都是空的——
它比"少配了一项"严重得多：它造出来的是一个**看起来正常但什么都没接上**的账号，
而使用者只会以为自己权限不够。所以：

- 服务端 `scopes` 是 `min_length=1`，且**先把范围解析完再落账号行**；
- 界面那一个下拉框下面有一行小字写明这件事，而且**拉不到选项就拒绝打开弹层**；
- 列表上范围为空的行出琥珀色的「未配置 · 看不到任何学生」，不是与别的行长得一样的 `—`。

### 3.8 关键服务算法

#### 3.8.1 "当前状态"口径：`latest_result_subquery`

`analytics_service.latest_result_subquery` 是
**"当前状态"这一口径的唯一来源**：每名学生只取 `latest_session_order()` 排在最前的那一场，
会话与结果**内连接**（名册里还没交卷的学生没有等级可数）。

```python
def latest_session_order():
    """按"最近一次交过卷的测评"排序。
    submitted_at 为 NULL 的排在后面 —— 所以"最近一场"是最近一次交过卷的，
    不是最近一次开过卷子的。"""
```

**他更早有一场已交卷时，取的就是那一场。** 这一条 2026-09-17 之前写反过——
注释（和 `CLAUDE.md`）说"刻意**不**回退到他更早的那一场"，
而 `latest_session_order()` 把 `submitted_at IS NULL` 排在**后面**，
所以"最近一场"是最近一次**交过卷**的。用探针跑出来才发现，注释与实现已经对齐。

**这不是将就**：若开卷即掉出"已测评"，普查周里学校的关注人数与分母会随
每个人的开卷动作上下跳。**一场都没交过的学生仍然没有等级**——
"还没测"与"测了没事"不是一回事。

**为什么不用 `max(id)`**：导入的会话（`source=IMPORTED`）id 更大但测评日期可能更早。

| 口径 | 用在哪 | 回答的问题 |
|---|---|---|
| **按人取最近一场** | 个案详情、重点学生、受控导出、工作台、统计分析、`GET /students/results` | "他**现在**是什么状态" |
| **按场** | 任务完成明细（`task_service.task_completion`）、完成率 | "**这一批人这次**测出了什么" |

按场那个是 2026-09-17 补的，当时给完成明细加了两列（关注等级 / MHT总分），
而它是模块里**唯一**按场说话的地方：一名学生落在两个批次里时，两边各自显示各自的分。
若哪天有人把它换成"按人取最近一场"，九月十六日那批的明细里会印出九月十七日的分——
一份批次报表说别的批次的事，而它旁边那列完成率还是按场算的。

#### 3.8.2 小样本护栏

```python
MIN_COHORT_FOR_AGGREGATE = 5
```

**分母小于 5 时不下发比率与均值**，只说"样本过小"
（`rate_or_none` / `_average_or_none` 返回 `None`）。

**计数不受这条限制**：学校要能回答"我这几个学生里有几个需要关注"，
所以「需关注 3 人」照给，「3 人里 2 人、60%」不给——三个人的百分比等于点名。

**`None` 不是 `0`**，两者在界面上必须长得不一样：
`0` 是"一个都没有"，`None` 是"这几个人算出来不足为凭"。
前端因此有 `rateText(rate, small)` → 「样本过小」，
`api.ts` 里对应的类型是 `number | null`——**不要用 `?? 0` 把它抹平**。

#### 3.8.3 任务状态的现算：`effective_task_status`

2026-09-17 之前 `assessment_task.status` 那一列是写入时定死的一个字面量：
建任务写 `ACTIVE`，导入批次也写 `ACTIVE`，然后再**没有一行代码读它或改它**。
于是任务列表上每一行永远显示"进行中"——一批 3/3 全收齐的外部导入、
一场已经过了截止日期的普查、一场还没到开始日期的复测，长得一模一样。
词汇表里的 `DRAFT` / `PAUSED` / `CLOSED` 从来没有写入方。

判据只有一个，由**已经被记下来的事实**推出来：

| 事实 | 状态 |
|---|---|
| 库里那一列不是 `ACTIVE` | 以库里为准（人写的 `DRAFT` / `PAUSED` / `CLOSED` 不可被推导盖过） |
| 还没到 `start_at` | `NOT_STARTED` 未开始 |
| 过了 `end_at` | `CLOSED` 已结束，**不管还有没有人没答** |
| 目标行全部完成（且总数 > 0） | `CLOSED` 已结束 |
| 其余 | `ACTIVE` 进行中 |

**两个消费者必须共用它**：任务列表（`list_assessment_tasks`）与
"学生能不能新开一张卷子"（`assessment_service.create_or_get_session`）。
界面说"已结束"时那个端点就真的开不了。

**口径是整场任务，不是读者的范围**：状态与 `name` / `start_at` 一样是任务自身的属性，
跟着范围走的是完成率。传进 `effective_task_status` 的两个数必须是
**不加范围谓词**的（`task_target_counts`）。否则一个只带 `CLASS` 范围的心理老师
会把一场 12/40 的普查看成"已结束"，同一行里状态说结束、完成率说 30%。

**"已结束"不等于"把人踢出卷子"**：`create_or_get_session` 里那道门排在
"已有会话直接返回"**之后**。截止日期管的是"还能不能再开一份新卷子"，
不是"手里这份还算不算数"；写在前面的话，窗口关闭那一刻答到一半的学生会拿到 404，
连答案都存不下去。

**窗口要能延长**：判 `CLOSED` 之后，"还有几个人没答，延一周"的出路是
`PATCH /assessment-tasks/{id}` 改 `end_at`。判据里**没有**人工关闭/重开这条路径——
四个码有了，按钮还没有。

**连带改动**：`seed.py` 的 `TASK-2026-FALL-MHT` 窗口从写死的
`2026-09-01 — 2026-09-30` 改成相对今天算。这条必须一起改：
判据开始读 `end_at` 之后，写死的窗口一到日子就会让
`test_assessment_api.py` 里每一条"学生开一份卷子"的用例拿到 404，
红的原因却不是功能坏了。

#### 3.8.4 完成率与目标行

`assessment_target` 是"这一场要测谁"的**快照**。这一点有产品含义：

- 任务发放时按创建者数据范围把学生**固化**成目标行；
- 之后名册新增的学生**不会**自动加进已有任务；
- 因此「导入全了名单，能查出谁没参加测评吗」的答案是：**能，但要在任务发放之后导入**。
  任务发放**之前**导入的名册不会被算进目标行。

完成率 = 已完成目标行 / 目标行总数，全部按场计算，不加范围谓词（§3.8.3）。

#### 3.8.5 提醒（工作台待办）

`GET /counselor/reminders` 是**两个来源各自封顶 20 条**（`REMINDER_LIMIT`）
之后报 `total`（另一次 `SELECT COUNT`）与比出来的 `truncated`。

```json
{ "items": [...], "total": 47, "truncated": true }
```

**为什么不能只回 `items`**：`items.length` 回答不了"我有多少待办"——
一个老师手上 40 条时它也说 20，面板那颗徽章于是无论 20 条还是 400 条都写「20 项」。
工作台据此写「另有 N 项未显示」。

**两个来源各封各的上限（不是一个共享的上限）**，否则这周 40 条跟进会把
复测计划整个挤掉。**计数与取数共用同一个 `where`**，所以 `total` 与 `items`
不可能各说各话。

**这是一个"凡是截断，都要自己说出来"的例子。** 全站现在有五处上限，
每一处都有一句"还有多少没显示"加一条出路：

| 位置 | 上限 | 那句话 |
|---|---|---|
| 工作台提醒 | 每来源 20 条 | 「另有 N 项未显示，请到「重点学生」逐条处理」 |
| 工作台队列 | 20 份 | 「另有 N 份一般观察档案」 |
| 题库导入预览 | 20 题 | 预览标题里写明 |
| 学生导入预览 | 20 行 | 预览标题里写明 |
| 任务完成明细 | 200 条 | 「导出CSV」 |

静默丢数据与"这里就只有这么多"在屏幕上长得一模一样，
而读者会照那个数安排工作。

#### 3.8.6 指标卡与它指向的列表必须同源

2026-09-17 修的一处：工作台的「逾期跟进」此前读的是后端 `metrics.following`，
即 `status == FOLLOWING` 的**档案**数，而这张卡点进去的是
`/counselor/cases?filter=overdue`，也就是 `c.overdue === true` 那一批。
真实数据上两者一个读 10、一个 0 条——**卡片与它自己指向的列表各说各话**，
而读者会照那个数去安排工作。

现在它从 `cases` 数组里现算（`overdueCount`），与队列同一个来源，
**构造上不可能漂**；`following` 没浪费，挪到脚注当上下文（「跟进中 10 份」）。

同一张卡上的「重点题命中」单位也从"人"改成"条"：
`pending_risk_events` 数的是 `risk_event` 的行，而引擎对**每一道命中的重点题**
各写一行（MHT 有两道：85 / 97），所以"一个人两道都中了"会被读成两个人。

**新增任何指标卡时先问一句"它点进去是什么，那个列表按什么筛"**，
两边不同源就得现算。

#### 3.8.7 导出：现算遮蔽与按人去重

**遮蔽是读取时现算的，不是回填列。** `export_service.mask_student_name`
在读取时算出"姓 + 同学"。`student.masked_name` 这一列**不是隐私控制**——
三条写入路径（`seed`、`seed_demo`、`student_import_service`）写的都是真名，
这一列在生产里和 `name` 一样实；它的用途只是花名册与关怀队列的**展示名**。

**为什么现算**：现算永远是对的，回填列会再次漂移。

**导出审计必须记录遮蔽模式**（`_export_detail` 拼进 `detail`）：
同样的 action、同样的 resource_type、同样的 purpose，
遮蔽与实名两条行长得一模一样，轨迹就答不上"这份文件是不是实名的"。
`purpose` 是自由文本，担不起这个字段。

**受控导出的"导出人数"按人去重，不是按档案行数。** 后端逐**学生**写行
（`export_service.py` 的 `seen_students`），而"重点学生"列表一行一份**档案**——
一名学生可以同时有已关闭的旧档案与在办的新档案，所以把 `cases` 的行数
填进「导出 N 人」那一格会比真实人数大。`CasesPage` 的 `exportCount` 因此
对高度关注那一支取 `new Set(...student_id).size`。

**这类数字（人数、条数）与它点进去/导出来的那个集合必须同源。**

## 4. 评分引擎详细设计

`backend/app/scale_engine/engine.py`，348 行，**纯函数，不碰数据库**。

### 4.1 输入与输出

```python
@dataclass(frozen=True)
class ScaleRuleConfig:
    question_count: int
    validity_questions: frozenset[int]
    key_questions: frozenset[int]
    validity_retest_threshold: int
    total_bands: tuple[ScoreBand, ...]
    dimension_bands: tuple[ScoreBand, ...]
    interpretations: ...

@dataclass
class ScaleCalculation:
    validity_score: int
    validity_status: str          # VALID / INVALID / ...
    total_score: int
    total_level: str              # GENERAL_RANGE / NEEDS_ATTENTION / KEY_ATTENTION
    dimensions: list[DimensionScore]
    risk_events: list[RiskEventDraft]
```

引擎的输入是"答案字典 `{题号: 选项码}` + `ScaleRuleConfig`"，
输出是一个 `ScaleCalculation`。**它不知道自己是第几次测、是谁测的、什么时候测的。**

### 4.2 默认规则配置

```python
DEFAULT_RULE_CONFIG = ScaleRuleConfig(
    question_count=100,
    validity_questions=frozenset({82, 84, 86, 88, 90, 92, 94, 96, 98, 100}),
    key_questions=frozenset({85, 97}),
    validity_retest_threshold=7,
    total_bands=(
        ScoreBand("GENERAL_RANGE",    0, 55),
        ScoreBand("NEEDS_ATTENTION", 56, 64),
        ScoreBand("KEY_ATTENTION",   65, 90),
    ),
    dimension_bands=(
        ScoreBand("LOW",    0, 3),
        ScoreBand("MEDIUM", 4, 7),
        ScoreBand("HIGH",   8, 15),
    ),
    interpretations=DEFAULT_INTERPRETATIONS,
)
```

### 4.3 总分：只累加内容题

```
total_score = Σ score(q)  for q not in validity_questions
```

**10 道效度题（82 84 86 88 90 92 94 96 98 100）不计入总分**，
所以 100 题的问卷总分上限是 **90**（100 − 10 道效度题，每题最高 1 分）。
分段的上界 90 就是这么来的。

效度题单独算出 `validity_score`（命中几道），
与 `validity_retest_threshold=7` 比较得出 `validity_status`。
效度异常的含义是"这份答卷的回答模式本身可疑"，
处置是**建议复测**（`retest_reasons` 里有「效度异常复测」这一条），
而不是任何形式的结论。

### 4.4 维度归属

```python
def dimension_for_question(question_no: int) -> str | None:
    #  1–15  LEARNING_ANXIETY      学习焦虑
    # 16–25  INTERPERSONAL_ANXIETY 对人焦虑
    # 26–35  LONELINESS            孤独倾向
    # 36–45  SELF_BLAME            自责倾向
    # 46–55  SENSITIVITY           过敏倾向
    # 56–70  PHYSICAL_SYMPTOMS     身体症状
    # 71–80  PHOBIC_TENDENCY       恐怖倾向
    # 81–99  odd numbers only      冲动倾向
    # else   None（含效度题 82..100 与题 100）
```

**维度是英文编码，不是 A–H 单字母。** `dimension_for_question`
与前端 `labels.ts` 的 `DIMENSION_LABELS` 必须一致——
`test_status_vocabulary.py` 与 `e2e/vocabulary.spec.ts` 两边把守。

维度分段 `LOW 0–3 / MEDIUM 4–7 / HIGH 8–15` 的上界 15 来自
**最长的一个维度有 15 道题**（学习焦虑 1–15）。前端 `DIMENSION_FALLBACK_MAX = 15`
是同一个数的镜像。

### 4.5 风险提示的生成

```python
risk_events = [
    RiskEventDraft(risk_type=..., risk_level=..., trigger_rule=...)
    for q_no, answer in answers.items()
    if answer == "YES" and by_no[q_no].is_key_question
]
```

**只有关键题（MHT 是 85 / 97）答"是"才生成风险提示**，且**每题各一行**。
这就是 §3.8.6 里"一个人两道都中了会被读成两个人"的来源。

**总分落入 `KEY_ATTENTION` 区间也会触发关注**，但那一条走的不是 `risk_events`，
而是 `total_level` 本身——档案的开启判据是两者的**或**：

```
命中任一关键题（答"是"）  或  总分 ∈ [65, 90]
        ↓
maybe_raise_risk_events() → risk_event + student_care_case
```

**这是筛查口径，不是诊断口径。** 引擎输出的 `trigger_rule` 记录的是
"哪一条规则被触发了"（如 `KEY_QUESTION_85`、`TOTAL_BAND_KEY_ATTENTION`），
`risk_level` 记录的是关注档位（`KEY_ATTENTION` / `NEEDS_ATTENTION`），
`dimension_result.interpretation` 是**维度得分区间的说明文本**。
三者都不产出、也不允许产出"患有某种心理疾病"式的表述。

### 4.6 规则版本化

`assessment_result.rule_version`（varchar 64）记录"这条结果当时按什么标准判定"。
完整规则标识由 **`scale_rule_service.rule_version_for(code, version)` 统一生成**：

```
MHT + MHT-1.1.0  →  MHT-RULE-1.1.0
```

种子、规则编辑、题库导入三个创建方都走它，免得三个地方各写一种形状。

**标识里不得出现生命周期词。** 规则行比草稿活得久，量表发布之后它仍然是
`ACTIVE` 的那一行，`MHT-1.1.0-RULE-DRAFT · 生效中` 这种自相矛盾的标签
就是这么渲染出来的（2026-09-16 修）；而且 `_bump_version` 取**尾部**数字，
以词结尾的名字会 bump 成 `...-RULE-DRAFT-2`，从此不再像版本号。

**改规则的两种情形**（这是"阈值属于量表规则版本，不属于系统配置"的直接后果）：

| 改的是 | 做法 | 已有结果 |
|---|---|---|
| **已发布**版本 | 生成新版本（`1.0.0 → 1.0.1`），旧版本标 `RETIRED` 保留 | **不受影响**（它们记着旧的 `rule_version`） |
| **草稿**版本 | 就地修改 | 不存在用它的结果 |

**阈值为什么不能放 `system_setting`**：那会让一次误改追溯改写所有历史结果的解释。
`assessment_result.rule_version` 要能回答"这条结果当时按什么标准判定"，
所以阈值必须与它一起被版本化。

**保存前校验**：分段连续、无重叠、无断档，且效度题/重点题必须在量表实际题号范围内。

### 4.7 草稿不生效，发布归管理员

- 题库导入只创建 `status="DRAFT"` 的版本，不参与评分，新建任务也不会选中它；
- 只有 `POST /scales/versions/{id}/publish` 把它变成 `PUBLISHED`，
  同时把同量器上一个已发布版本转为 `ARCHIVED`（**保留，不删除**）；
- **导入开放给管理员 + 心理老师，发布与改规则只归管理员**，两者都写审计。

## 5. 数据库详细设计（含完整 DDL）

### 5.1 四层事实模型

这是整个数据设计的**组织原则**，也是最重要的一条不可破坏约定：
**四层互不覆盖**。每一层只追加，不改写上面一层。

| 层 | 表 | 语义 | 谁写 |
|---|---|---|---|
| ① 原始答题事实 | `assessment_session` · `assessment_answer` | 学生实际提交了什么 | 学生答题路径，**一次写入，永不修改** |
| ② 量表计算事实 | `assessment_result` · `dimension_result` | 按某个规则版本算出了什么 | 交卷时算一次，携带 `rule_version` |
| ③ 学校管理事实 | `assessment_task` · `assessment_target` · `risk_event` · `student_care_case` | 学校组织了什么事、发现了谁 | 心理老师 / 管理员 |
| ④ 专业工作事实 | `manual_review` · `follow_up_record` · `family_contact_record` · `retest_plan` | 人做了什么专业判断与工作 | 心理老师 |

两条从这条原则直接推出的禁令：

> **人工复核不得修改原始答卷；关闭档案不得删除历史记录。**

**这条的后半句在 2026-09-17 被两个 bug 各证伪过一次，两个都修了：**

**① `student_care_case` 上那个 `UniqueConstraint("student_id", "status")` 已删除**（迁移 `0012`）。
它把"同一时间只有一条在办"当成了数据库约束，而**已关闭**的档案恰恰会累积：
上学期关掉的是一次完整的关怀过程，这学期再出状况是一条新的过程。
约束还在时第二次关闭撞 UNIQUE、`db.flush()` 抛 `IntegrityError`，用户拿到 500——
**秋季关档、春季再关一次**是学校每年都会遇到的时序。

现在"只有一条在办"由写入侧保证（`assessment_service.open_or_reuse_care_case`
先找非 `CLOSED` 的那条，找不到才新建）。

删除那条唯一索引前必须先建 `ix_student_care_case_student_id`：
它兼作 `student_id` 外键的索引，MySQL 会以 **1553** 拒绝删一条外键正在用的索引，
而**这条错误只有真库会报**（内存 sqlite 不跑 Alembic）。

**② `care_service.get_care_case` 不再过滤 `CLOSED`**，
同一条学生的档案有多条时取 **id 最大**的那条（与 `open_or_reuse_care_case`
选"当前档案"的口径一致）。此前它 `where(status != CLOSED)` 的写法让"关闭"这个动作
把自己脚下的页面抽掉了：`closeCase()` 成功之后紧接着重新拉详情，
拿到 404「关注档案不存在」。

> **同一个"关闭"，三个列表三种取舍，各自的理由都写在该处：**
> - `get_care_case` **不过滤**（关闭之后这一页还得能看，否则关闭动作抽掉自己脚下的页面）
> - `list_care_cases` **不过滤**（它有「已关闭」页签，那一页签得有东西可列）
> - `analytics_service.leader_progress` **过滤**（那一页叫「重点进展」，
>   而一条 `CLOSED` 的档案没有进展可看）
>
> **这不违反"关闭档案不得删除历史记录"**——那条说的是别删行
> （个案详情照原样展示已关闭档案），不是每条列表都得列出来。

#### 5.1.1 `student.masked_name` 不是隐私控制

三条写入路径（`seed`、`seed_demo`、`student_import_service`）写的都是**真名**，
这一列在生产里和 `name` 一样实。它的用途只是花名册与关怀队列的**展示名**。
导出遮蔽由 `export_service.mask_student_name` 在读取时**现算**（姓 + 「同学」）。

#### 5.1.2 `student.age` 是存下来的整数，不是现算的

迁移 `0011_student_age` 把 `birth_date` 换成了 `age`，学生信息导入的最后一列
随之从「出生日期」改成「年龄」（年龄列认 `13` 与 `13岁`）。

0009 当初选的是"存出生日期、读取时现算"，理由是学生过完生日那一刻存下来的年龄就错了；
2026-09-17 按学校要求反过来——**学校手上的名册只有年龄，现算没有输入可算**。

代价是知情的：**这一列不会自己变**，不重导名册，界面上的年龄就停在去年。
所以 `assessment_import_service` 按年龄消歧时保留 **±1 岁的容错**
（那份文件可能是去年那次普查），而且它不再有"按测评日期算"这个口径可讲——
名册那边只有一个数。

**写入方因此有两个**：

1. 学生信息导入（整份名册）；
2. MHT 测评记录导入（`AGE_MISMATCH` 冲突选了「覆盖」时，只改这一名学生的年龄，
   `_update_roster_age`，写审计「更新学生年龄」）。

老模板（末列还叫「出生日期」）会被逐行挡下来：`DictReader` 会把那一列读成
没人认领的键，年龄于是整列 NULL，而每一行都 NULL 和"学校没填"长得一模一样。

**`user_account` 的两处设计说明：**

- `UNIQUE (account, account_type)` 而不是 `UNIQUE (account)`。

这就是 §3.7.1 里那两个 `is not None` 要防的"半填行"。

`ACTIVE`（在读）/ `INACTIVE`（已离校）。已离校的学生仍在名册上、
仍能看到历史测评，但不会被新建任务选中。

**`uq_session_task_student (task_id, student_id)`** 是"一名学生在一场任务里只有一份答卷"
的物理保证。注意 `task_id` 可空——`NULL` 在 MySQL 唯一索引里**不参与去重**，
所以脱离任务单独开的会话（导入路径的 `task_id` 非空，这里指理论上无任务的会话）
不互相冲突。

**`assessment_answer.answer` 是 `varchar(8)`**：MHT 的选项是 `YES` / `NO`，
其余量表可能是别的短码。`score` 是**当时**由引擎算出的分并**存下来**——
不是每次读时重算。这样即使规则改了，这一行的分仍然是当时那个规则算的。

**`source` 列**（迁移 `0010_import_source`）：
`IN_SYSTEM`（系统内作答）/ `IMPORTED`（校外平台导入）。默认 `IN_SYSTEM`。
它是"数据从哪来"的标记，下游（统计、导出）据此判断口径。

**`duration_seconds`** 是交卷时算出来存下的（`submitted_at - started_at`），
不是每次读时算——因为 `started_at` 可空，且"用时"是一个应当被固定下来的事实。

### 5.4 索引与约束策略

#### 5.4.1 外键全部 RESTRICT，没有 `ondelete=`

```
全库 45 个外键约束（24 张表，`SHOW CREATE TABLE` 里逐条数出来），
ondelete 一律是默认值（RESTRICT），没有一个是 CASCADE / SET NULL。
```

这不是疏漏，是**刻意的**，而且它有直接的产品含义：

| 表 | 被谁引用 | 删一行会怎样 |
|---|---|---|
| `user_account` | `audit_logs` / `manual_review` / `follow_up_record` / … | 轨迹与工作记录全部悬空 |
| `risk_event` | `manual_review` | 复核记录悬空 |
| `assessment_session` | `risk_event` / `retest_plan` | 风险提示与复测计划悬空 |
| `student` | 关怀档案 / 测评 / 风险事件 / 账号范围 | 全链路悬空 |

**直接后果一：没有删除接口。** 账号是"停用 ≠ 删除"（§3.5.2），
学生是"离校 = `status` 改成 `INACTIVE`"，档案是"关闭"。
每一处都是改状态，不是删行。

**直接后果二：清库脚本的删除顺序是被约束逼出来的。**
`app/db/purge.py` 的删除顺序有测试把守（`test_purge_demo.py`），
而 `backend/sql/reset_to_baseline.sql` 的删除顺序由
`test_sql_reset_to_baseline.py` 按 `Base.metadata` 的外键图重推一遍。

**这一条为什么危险**：`tests/conftest.py` 的内存 SQLite
**默认不检查外键**（`PRAGMA foreign_keys` 默认关闭），父行先删在 sqlite 上照样全绿，
而在 MySQL 上是必然的 **1451**。`make reset-db` 原来那段内联脚本就是这么坏的
（`risk_event` 排在 `manual_review` 之前，而 10 行 `manual_review` 正引用着活着的 `risk_event`）。

`test_purge_demo.py` 自建引擎并在 `connect` 事件里开 `PRAGMA foreign_keys=ON`——
pragma 在事务里是空操作，必须**在连接建立时**设。
这个模式值得复用：**凡是"只有真库才会报"的约束，测试要么用真库，要么自己在 sqlite 上把约束打开。**

#### 5.4.2 索引命名：两种风格并存，各有原因

| 风格 | 例子 | 谁生成的 |
|---|---|---|
| MySQL 自动命名 | `grade_ibfk_1`、`student_id` | 外键与 `index=True` 的默认名 |
| 显式命名 | `uq_student_school_no`、`uq_answer_session_question`、`ix_audit_log_student_id`、`ix_student_care_case_student_id` | 有语义的唯一约束与显式 CREATED INDEX |

- **唯一约束全部显式命名**（`uq_` 前缀）：它们出现在业务错误里，
  `uq_session_task_student` 比 `assessment_session_ibfk_3` 更能说明发生了什么。
- **两个普通索引显式命名**（`ix_` 前缀）：`ix_audit_log_student_id`（迁移 0006）
  与 `ix_student_care_case_student_id`（迁移 0012）。
  后者尤其重要——它必须在唯一索引被删**之前**建好，
  否则 MySQL 以 **1553** 拒绝（"Cannot drop index needed in a foreign key constraint"）。
- **其余普通索引用 MySQL 默认名**（就是列名本身）：它们没有语义，
  只是外键的配套索引。

**这套命名的不一致是历史产物，不是设计。** 迁移 0001–0012 由不同阶段写成，
统一命名需要一次纯 DDL 迁移（改索引名 = drop + create），
而收益只是好看。**不改。**

#### 5.5.1 revision id 必须 ≤ 32 字符

`alembic_version.version_num` 是 `VARCHAR(32)`。**超长不会在 `ADD COLUMN` 处报错**——
DDL 先提交、版本戳的 `UPDATE` 才失败（MySQL 的 DDL 不在事务里），
库变成"已迁移但仍记在上一个版本"，下次 `upgrade` 撞 `Duplicate column`。

当前最长的 id 是 `0009_student_profile_duration`（29 字符），
余量 3 个字符。**`__pycache__` 里还留着一条 33 字符的旧 `.pyc`**
（`0009_student_profile_and_duration.cpython-311.pyc`），是改名前的残骸——
它不在 `versions/` 里，Alembic 不会加载它，但它**说明这条规则正在被踩**。

**这条规则写在每一条迁移的 docstring 里，却没有任何测试把守。** 见 §10 技术债 T-04。

#### 5.5.2 五条"有故事"的迁移

**0006**：`student_id` 加进 `audit_log` 的同时**显式建了索引**。
如果用 `index=True`，Alembic 自动生成的名字是 `ix_audit_log_student_id`，
与显式建的名字一样——但它是由 `op.create_index` 产生的，
不是 `op.add_column` 的副作用。这样写是为了让"这一列需要索引"是一个**决定**，
不是一次自动推导。

**0009 → 0011**：`birth_date` 被创建，然后被删除。这是 §5.1.2 那段历史的物理痕迹。
**0011 里的 `DROP COLUMN birth_date` 会让该列上的数据全部丢失**——
如果有人在生产库上跑过 0009 并且已经导入了出生日期，0011 会把它删掉。
当前 0009 与 0011 之间没有任何写入方（学生导入那时写的是 `birth_date`），
所以实际影响是"那段时间导入的出生日期没了"。

**0012**：这条迁移的**语句顺序**是它的全部价值，
而顺序错了只有真库会报。`op.create_index("ix_student_care_case_student_id", ...)`
必须排在 `op.drop_constraint("uq_care_case_student_status", ...)` **之前**。
反过来的话 MySQL 报 1553。

**0003**：给 `assessment_session` 加 `task_id` 时用了具名外键 `fk_session_task`，
而其余外键是 MySQL 自动命名的。这是这条迁移唯一一处显式命名。

#### 5.5.3 测试库与生产库的建表方式是**两套**

| | 生产 / 开发 | 测试（pytest） |
|---|---|---|
| 建表方式 | `alembic upgrade head` | `Base.metadata.create_all(engine)` |
| 数据库 | MySQL 8 | 内存 SQLite |
| 约束检查 | 全开（外键、唯一、类型、长度） | 外键**默认关闭**；类型宽松；无长度限制 |
| `server_default` | 迁移里写的那些都在 | **metadata 里没有的一律不给** |

**这就是下面那一节差异的来源。**

### 5.6 已实测的两处偏差

以下两条是**在真库上跑出来的**，不是读代码推的。记在这里是因为
它们**都不影响功能**，但都会在排查问题时把人带偏。

#### 5.6.1 20 列有服务端 `DEFAULT`，而 ORM metadata 里一列都没有

**验证方法**：在一个全新的 MySQL 库上跑 `alembic upgrade head`，
然后把 `information_schema.columns` 与 `Base.metadata` 逐列比对。

**结果**：表名、列名、可空性**完全一致**（24 张表一处不差，零个缺列，零个可空性不符）。
**但 20 列在迁移库里带 `DEFAULT`，而 ORM metadata 不产生它们**，
反方向（metadata 有、库里没有）是 0 列：

> 在 §5.3 那七段 DDL 里数 `DEFAULT '` 会数出 **22** 个，不是 20——
> 多出来的两个是 `assessment_task.source` 与 `assessment_session.source`
> 的 `DEFAULT 'IN_SYSTEM'`（迁移 `0010` 加的），那两列**在 ORM 里也有**，
> 所以不属于下面这张表。22 − 2 = 20。

| 表.列 | 库里的 DEFAULT | ORM |
|---|---|---|
| `school.status` | `'ACTIVE'` | 无 |
| `grade.status` | `'ACTIVE'` | 无 |
| `grade.sort_order` | `'0'` | 无 |
| `class_group.status` | `'ACTIVE'` | 无 |
| `student.status` | `'ACTIVE'` | 无 |
| `user_account.active` | `'1'` | 无 |
| `user_account.failed_attempts` | `'0'` | 无 |
| `user_account.must_change_password` | `'1'` | 无 |
| `assessment_scale.status` | `'DRAFT'` | 无 |
| `scale_question.status` | `'ACTIVE'` | 无 |
| `scale_question.is_validity_question` | `'0'` | 无 |
| `scale_question.is_key_question` | `'0'` | 无 |
| `scale_rule.status` | `'ACTIVE'` | 无 |
| `assessment_task.status` | `'ACTIVE'` | 无 |
| `assessment_session.status` | `'IN_PROGRESS'` | 无 |
| `assessment_target.status` | `'NOT_STARTED'` | 无 |

| `follow_up_record.status` | `'ACTIVE'` | 无 |
| `retest_plan.status` | `'PLANNED'` | 无 |

**为什么会有这个差异**：这些 `server_default` 是迁移里**手写**的
（`sa.Column(..., server_default="ACTIVE")`），而模型定义里写的是
`Mapped[str] = mapped_column(String(32))`——模型**从来没有**声明过服务端默认值，
默认值是服务层显式赋的。

**后果一（好的）**：迁移库比测试库**更宽容**。一条只给了部分列的
原始 `INSERT` 在生产库上会成功并填上默认值，在测试库上会因为
`NOT NULL` 失败。这正是"模型与迁移漂移不会被测试发现"（`CLAUDE.md` 缺口 3）
的一个**具体形状**。

**后果二（需要知道的）**：两套 schema 不是同一个 schema。
任何"在测试里建表、在开发库上跑真数据"的验证都需要意识到这一点。
当前的代码**不依赖**这些默认值（服务层每处都显式赋值），
所以功能上没有影响——但**依赖它们的新代码会在测试里红、在生产里绿**，
而红的原因看不出来。

**要不要修**：把这些 `server_default` 补进模型定义（或从迁移里去掉）。
两条路都可以，但都需要一次决定，而且改模型会让 `create_all` 出来的表
与现有迁移库仍然不同（`create_all` 不 ALTER 已存在的表）。
**本文记录它，不改它**——因为它当前不造成故障，而为它做一次改动会
波及全部 20 列与所有依赖显式赋值的路径。

#### 5.6.2 时区：`created_at` 比同一行的 Python 写入列**早 8 小时**

**验证方法**：
```sql
SELECT @@global.time_zone, @@session.time_zone, now(), utc_timestamp();
-- → SYSTEM, SYSTEM, 2026-09-18 19:47:48, 2026-09-18 11:47:48
```

**`@@session.time_zone` 是 `SYSTEM`，而目标机是 UTC+8。**

`models/common.py` 的 `TimestampMixin` 上有一段专门的 docstring：

```python
class TimestampMixin:
    """Row bookkeeping timestamps.

    These two are the only timestamps in the schema the *database* writes
    (`server_default=func.now()`); every other one — `started_at`,
    `submitted_at`, `answered_at`, `calculated_at` — is written by Python from
    `assessment_service.now_utc_naive()`, i.e. UTC. On MySQL `func.now()` is
    `CURRENT_TIMESTAMP` evaluated in the server's session time zone, which is
    `SYSTEM` (here UTC+8), so `created_at` lands 8 hours ahead of the
    Python-written column on the very same row. [...]

    `DateTime(timezone=True)` does not help: it is a no-op on MySQL, where the
    column is a plain DATETIME.
    """
```

```python
def now_utc_naive() -> datetime:
    return datetime.now(UTC).replace(tzinfo=None)     # ← 无 tz 的 UTC 时间
```

**具体表现**：一行 `assessment_session` 上，
`created_at`（数据库写的）读出来是 `19:47`，
而同一行的 `started_at` / `submitted_at`（Python 写的）是 `11:47`。
**差 8 小时，在同一行上。**

**为什么不修**：

- `DateTime(timezone=True)` 在 MySQL 上**是空操作**，列就是普通 `DATETIME`，
  改类型不改行为；
- 把 `func.now()` 换成 Python 的 UTC 会让 `created_at` 的语义变成"应用服务器的时间"，
  而它现在的语义是"数据库服务器的时间"——后者在网络分区场景下更可信；
- 统一成一个时区需要一次数据迁移（把已有 `created_at` 减 8 小时），
  而**没有一条业务逻辑跨这两类列比较时间**（"最近一场"用的是
  `submitted_at`，全部由 Python 写；审计列表只按 `created_at` 自己排自己）。

**唯一的风险是排查时被它带偏**：看到 `created_at` 比 `submitted_at` 晚 8 小时
会以为数据有问题。所以这条记在 docstring 里，也记在这里。
**排查时间相关的问题前，先跑一次 `SELECT now(), utc_timestamp()`。**

### 5.7 清库：两条路径，各自管各自的机器

2026-09-17 用户要求"清除 mock 数据，仅保留管理员账号和基本配置"，
并要一份**能在新环境上运行**的 SQL。两件事的落点不同：

| | `make purge-demo` | `backend/sql/reset_to_baseline.sql` |
|---|---|---|
| 在哪跑 | 这台机器（开发机） | 任何一台装了 mysql 客户端的机器 |
| 清到什么 | `seed.py` 的基线（**留着** `S001`、两名种子员工、基线任务） | 只有 `admin` + 基本配置（**名册、员工、任务全没**） |
| 怎么实现 | `app/db/purge.py`，ORM | 纯 SQL，一个事务 |
| 谁调 | `make reset-db`（`purge reset`）/ `make purge-demo`（`purge demo`） | 手工 |

**那份 SQL 只删行，不建表也不建行。** schema 归 `alembic upgrade head`，
基线行归 `python -m app.db.seed`。正确用法：

```bash
make migrate && make seed          # 或者在一个已经迁移过的库上
mysql -h HOST -u USER -p DB < backend/sql/reset_to_baseline.sql
```

**不把"基线"写成 SQL 的 INSERT**：那三样各自在仓库里**只有一个出处**——
admin 的密码哈希（`seed.py` 的哈希函数）、100 道题的题干（`data/mht_scale.json`）、
评分规则 JSON（`DEFAULT_RULE_CONFIG`）。在 SQL 里再抄一份必然漂移，
而一份抄错的规则 JSON 会让那个库的评分与别处不同、且看不出来（§4.6）。
**这是一条约定，不是没写完。**

**三条由 `test_sql_reset_to_baseline.py` 把守的不变量：**

1. **覆盖面与 `purge.py` 对齐**：`ASSESSMENT_TABLES` 里的表，SQL 里必须都出现。
   同一件事在 Python 与 SQL 各写一份，比对是唯一能让它们不漂的办法。
2. **子先父后，或那条出处列先被置空**，二者认一个。
   两条出路各有各的用处：调顺序解决得了 `user_scope.student_id → student`（两张都删），
   解决不了 `role_permission.updated_by → user_account`（前者整表保留，只能置 NULL）。
   **`role_permission` / `system_setting` / `assessment_scale` 上那三列是全脚本
   唯一被改动的保留内容**，改的是"谁动过它"的出处，不是配置本身；
   重新指到 admin 上会是一句谎话，所以置 NULL。
3. **每一条 `DELETE` 都挂在 `@admin_id` 上**，找不到 admin 时一条都不删。
   最坏的失败不是"少删了"（再跑一次的事），而是"删完没有人能登录"。

**一个只在真环境上才看得见的差别**：全新库的 `system_setting` 与 `role_permission`
是 **0 行**（配置回退 `DEFAULTS`、权限回退 `CAPABILITY_DEFAULTS`，§3.6.4），
`seed.py` 本来就不写它们。脚本一行都不碰这两张表——
一个库上有几行，取决于那个库的操作员配过什么。
**别照着开发库的 2 行 / 20 行去断言它。**

### 6.3 账号与权限 `admin-accounts` / `admin-permissions`

| 方法 | 路径 | 权限 |

**两条创建路径，只有一条长期成立：**

| 角色 | 从哪来 | 为什么 |
|---|---|---|
| 学生 | **名册导入** | 学生的身份属性是学号/年级/班级/年龄，只有名册知道 |
| 心理老师 / 德育领导 / 系统管理员 | **「账号与权限」→ 新建账号** | 员工的身份属性是职责与所辖范围，与名册无关 |

**学生那一侧不为员工开口子。** `create_account` 收到 `role_code=student`
给的是**一句指路的 422**（"学生账号不在这里创建：学生跟着名册一起生成…"），
而不是一个"也行"的接受——否则走那条路建出来的学生会是一个
**没有学号也没有班级**的账号，登录得进来，测评记录里认不出他是谁。

**数据范围必填**（`scopes: min_length=1`），且**先把范围解析完再落账号行**——
一个不存在的 `grade_id` 不会留下半写好的账号。

**`STUDENT` 级范围在这个入口被拒**（422）：把范围切到单人级要重新想反推风险（§10 缺口 G-02）。

**角色与账号创建后不可改**：`update_account` 只收
`display_name` / `scopes` / `active`。`authenticate` 是拿三个字段一起匹配的，
改其中任何一个都会让那个人的登录凭据在一夜之间失效，
而轨迹上只留下一行"更新账号"。**录错了就停用那一个、另建一个**——
那会留下**两条**审计，比一条静默改写的轨迹更接近发生过的事。

**审计用四个动作码，不用一个**：`新建账号` / `更新账号` / `停用账号` / `启用账号`。
其中"停用/启用"**另起一条**而不是并进"更新账号"：
审计页的搜索匹配的是 `action`，把停用塞进"更新账号"会让操作员
按眼睛看到的那个按钮名搜不到它。**密码一律不进 `detail`**——
`detail` 是会被导出的文本，写进去等于把凭据复制一份。

### 6.4 组织与学生 `students`

| 方法 | 路径 | 权限 |
|---|---|---|
| GET | `/students` | `ORG_ACCOUNT` ∈ {MANAGE, READ_BASIC} |
| GET | `/students/import/template` | `ORG_ACCOUNT: MANAGE` |
| POST | `/students/import/preview` | `ORG_ACCOUNT: MANAGE` |
| POST | `/students/import/commit` | `ORG_ACCOUNT: MANAGE` |

| GET | `/students/{student_id}/key-questions` | `KEY_QUESTIONS: GRANTED_WITH_AUDIT` + `purpose` 必填 + 范围 |

**`/students/results` 是那个"双门槛"端点**（§3.6.6）。

**`/students/{id}/key-questions` 的三道门**：
能力（`GRANTED_WITH_AUDIT`）+ 用途参数（`PURPOSE_REQUIRED`）+ 数据范围，
**且审计在返回数据之前写入**。

**学生导入的编号规则**（`student_import_service.check_grade_and_class`）：

- 班级按 `701 / 801 / 901` 编号，首位 `7/8/9` 分别是初一/初二/初三；
- **年级仍必填**，只认 `初一/初二/初三` 三个名字——写"七年级"会新建一个年级行，所以挡下来；
- 两列对不上按行报错（`班级 701 属于初一，与年级 初二 不一致`）。

留着冗余的年级列并强制一致，是因为 `commit_student_import` 只拿字符串去
`Grade.name` 里找、找不到就新建，不拦的话录错的学生会被**静默**挂到错年级下面。

**学号不校验格式**（`27025160101`）：各位数字的含义没有确认过，只校验必填与不重复。

**"学号已在名册上"是冲突，不是错误**：`preview` 把它放进 `conflicts`
而不是 `errors`，并回 `conflict_count`；处置是**文件级**的一次选择
（`resolution`: `overwrite` / `skip`）。**未选而文件里有冲突 → 422，且任何写入之前就拦。**

- **"文件内重复学号"仍然是错误**，刻意不升级成冲突：同一份文件里两行都说是同一个学号时
  没有"覆盖"可言。这问的不是口径，是文件坏了。
- **覆盖是就地改，不删了重建**（`_overwrite_student`）：`student.id` 被关怀档案、
  测评会话、风险事件、账号范围引用着，全库没有 `ondelete=`。
- **覆盖只改姓名的六列**：`name` / `grade_id` / `class_id` / `gender` / `age`，
  外加展示名 `masked_name` 与账号的 `display_name`。
  **学号不改**（它正是冲突的判据）；`status` 不改。
  `OVERWRITABLE_FIELDS` 是这句承诺的常量形式，
  `test_overwrite_touches_exactly_the_columns_it_promises` 快照每一列、
  断言"实际变化的列 == 承诺的那些"。
- **选填列（性别/年龄）文件里空着就跳过，不写 NULL**：
  "这一列我没填"与"把名册上这个数抹掉"是两件事。

**学生信息导入只有一个入口：「组织学生」（`/admin/organization`）。**
数据中心里的那份副本 2026-09-17 删掉了——它是 `v-if="isAdmin"`，
而 `/counselor/data` 的 `meta.role` 是 `counselor`、`AppLayout.vue` 会把
不匹配的角色弹回登录页，**两边都对不上，所以它对任何角色都不显示**。
死在 `v-if` 里的东西两个 e2e 角色用例都不会发现——它们各自走的是自己够得着的页面。

**`GET /care-cases/{student_id}/comparison`（班级对照）同时踩两条约定**（§3.6.5 + §3.7）：
它暴露**一名学生**的八维度得分，所以既要 `STUDENT_PSYCH_DETAIL: SCOPED`
（不是 `SUMMARY`）、又要 `ensure_student_in_scope`，并且**每次读都写审计**
（action `查看班级对照`、resource_type `STUDENT_CARE_CASE`）。
**归在 `/care-cases` 而不是 `/analytics` 就是这个原因**——它返回的是个体明细，不是聚合。
被拒时**不写审计**。

**`{case_id}` 与 `{student_id}` 两种路径参数混用是刻意的**：
详情按学生（一个学生只有一页），变更按档案（一个学生可能有多条档案）。
`POST` 那一组用 `case_id`，因为"关闭哪一条"必须明确。

### 6.10 审计 `audit-export`

| 方法 | 路径 | 权限 |
|---|---|---|
| GET | `/audit-logs` | `require_role(ADMIN, COUNSELOR, LEADER)` |
| POST | `/care-cases/export` | `CONTROLLED_EXPORT` 非 NONE |
| POST | `/care-cases/high-risk/export` | 同上 |
| POST | `/care-cases/{student_id}/export` | 同上 |

**审计日志的筛选/排序/分页全部在服务端**（`limit`/`offset`/`sort`/`order`/`q`/`actor_role`），

### 6.13 测评记录导入 `assessment-import`

| 方法 | 路径 | 权限 |
|---|---|---|
| GET | `/assessment-import/template` | counselor |
| POST | `/assessment-import/preview` | counselor |
| POST | `/assessment-import/commit` | counselor |

这条链路的设计要点（细节见 §10 缺口 G-03）：

- **只收 `.csv`**，按扩展名整份拒掉其它格式，并且**说清该怎么办**
  （学校手上的 `.xlsx` 由人"另存为 CSV"）；
- **`_read_csv` 认 UTF-8 与 GBK**：中文 Excel/WPS 在 Windows 上
  "另存为 CSV"写的就是 GBK，只按 UTF-8 解会变成一个 500，而那本该是"照读不误"；
- **判重按"月"为单位**（`month_bounds(tested_on)`），不是按天——
  学校把一次普查分两批导（先初一、隔几天再初二）时第二批会被挡在门外；
- **`AGE_MISMATCH` 与 `DUPLICATE` 是冲突，不是错误**：它们需要人做决定，
  所以既不进 `errors` 也不进 `warnings`。`preview` 把它们**一并放进 `preview_token`**
  （否则"覆盖上次"这条路走不通），并回 `conflict_count`；
- **`overwrite` 就地改写**那一场（答卷、结果、八维度、用时按新文件重算），不删了重建：
  `risk_event.session_id` / `retest_plan.source_session_id` 都指着这一行。
  重写时**只收回 `PENDING` 且无人复核的**风险事件——改完文件的重新导入
  不该留下两条同名待办，但心理老师写过的复核是工作记录，不能因为重导一次就消失；
- **`AGE_MISMATCH` 选 `overwrite` 时会写回名册年龄**（`_update_roster_age` + 审计
  「更新学生年龄」）——这与"性别只用来消歧、不写回"不同，是用户明确要求的那一条；
- **判定口径与系统内作答完全一致**：命中重点题（85/97）或总分落入重点关注区间时，
  与 `create_or_get_session` 一样调 `maybe_raise_risk_events`，同样开出风险提示与关怀档案。
  "一条只进统计、不进待办的记录在关怀队列里是不可见的，
  而学校导进来正是为了让老师看见"；
- **性别约定是 `2` 男 / `1` 女**（按学校手上的真实文件），性别**只用来消歧，从不写回名册**。
  学生信息导入走的是另一套约定（只认 `MALE`/`FEMALE` 或 `男`/`女`，**不认数字**），
  两条链路各管各的常量；
- **题号按表头映射，不逐字校验题干**：那份唯一的真实文件里 13/100 条是
  同一道题的措辞变体，逐字比对会把学校唯一的一份文件全拦下来。

### 6.14 接口设计的四条横向约定

**① 列表返回 `{items: T[]}`，封装函数统一拆成裸数组。两个例外**：
`getAuditLogs`（服务端分页，`{items, total}`）与
`getCounselorReminders`（`{items, total, truncated}`）。

**② 敏感读取先写审计，后返回数据。** 被拒时不写。

**③ 导出必须带 `purpose`，且 `detail` 里记遮蔽模式。**

**④ 不在日志里打印完整答卷、重点题回答或家庭回访正文。**

### 7.2 角色门禁的实现：没有路由守卫

`main.ts` **没有 `beforeEach`**。角色门禁靠 `AppLayout.vue` 拿到 `/auth/me` 后
比对 `meta.role`，不匹配就 `router.push('/login')`——**越权访问表现为"被弹回登录页"**。

这个设计的后果要一起记住：

- **后端鉴权是最终权限来源，前端隐藏不是安全措施。**
- 一个角色的页面永远到不了（如 admin 访问 `/counselor/data`），
  **这件事没有任何测试会发现**——`e2e` 的角色用例各自走的是自己够得着的页面。
  这正是"学生信息导入的副本"能一直挂着两个入口的注释却对谁都不显示的原因。
  **改名/搬页之后要问一句"旧的那份还到得了吗"**，到不了就是死代码。
- 同一个形状的另一处未修：`ScalePage.vue` 的发布按钮是**死代码**（详见 §10 技术债 T-03）。

### 7.3 API 层

`services/api.ts`，1315 行，其中约 1200 行是接口函数与 TypeScript 类型。

```ts
const API_BASE = '/api/v1'
const TOKEN_KEY = 'xlp_access_token'

async function apiRequest<T>(path: string, init: RequestInit = {}): Promise<T> {
  const response = await fetch(`${API_BASE}${path}`, {
    ...init,
    headers: {
      'Content-Type': 'application/json',
      ...(getToken() ? { Authorization: `Bearer ${getToken()}` } : {}),
      ...init.headers,
    },
  })
  const body = await response.json()      // ← 不是 JSON 时抛 SyntaxError
  if (!body.success) throw new Error(body.error?.message || '请求失败')
  return body.data
}
```

**四个要点：**

1. **`response.status` 从不被读**（§3.2 的②）。这是全站最需要理解的一条前端约定。
2. **列表接口拆裸数组的函数在 `api.ts` 里**，不在调用点。
3. `CurrentUser.scopes` 是 2026-09-17 才补的类型——**那一列一直在响应里，
   只是没有类型所以没有读者**。这是一类典型的"后端已经给了、前端不知道"的缺口。
4. **`api.ts` 是接口契约的前端镜像**，它没有生成器（不是从 OpenAPI 生成的）。
   代价是后端改字段前端不会自动红；收益是不需要构建期依赖后端。

### 7.4 `labels.ts`：唯一映射层与四面契约

`services/labels.ts`，400 行，是后端枚举码 → 中文的**唯一**映射层。
不得在各视图里重复定义。

#### 7.4.1 四张有键序意义的表

```ts
export const LEVEL_LABELS = { KEY_ATTENTION: '重点关注', NEEDS_ATTENTION: '需要关注', ... }
export const LEVEL_ORDER = Object.keys(LEVEL_LABELS)      // ← 由键序生成
```

| `*_ORDER` | 键序 | 语义 |
|---|---|---|
| `LEVEL_ORDER` | 重点关注 → 需要关注 → 一般观察 | **从重到轻** |
| `CASE_STATUS_ORDER` | 待复核 → 跟进中 → 观察中 → 已关闭 | 流程先后 |
| `TASK_STATUS_ORDER` | 草稿 → 未开始 → 进行中 → 已暂停 → 已结束 | 生命周期 |
| `SCALE_STATUS_ORDER` | 草稿 → 已发布 → 已归档 | 发布流程 |
| `STUDENT_STATUS_ORDER` | 在读 → 已离校 | — |
| `SOURCE_ORDER` | 系统内作答 → 外部导入 | 先自家后外部 |

`*_ORDER` 由映射表的**键序**生成，所以加新码时自己跟上。
**那几张表的键序是有意义的，加新码时想清楚它排在哪一端，不要顺手追加到末尾。**

`TASK_STATUS_LABELS` 与 `SCALE_STATUS_LABELS` 的键序 2026-09-17 为此**调过**
（前者原本 `ACTIVE` 打头、后者原本 `PUBLISHED` 打头），不是新加的键。

#### 7.4.2 四个面

| 面 | 谁在守 | 漏了会怎样 |
|---|---|---|
| 后端发出的编码 `labels.ts` 认不认 | `test_status_vocabulary.py` | 界面显示原始编码 |
| 视图有没有**调用**标签函数 | `e2e/vocabulary.spec.ts` | 界面显示原始编码 |
| 服务端生成的导出文件认不认 | `test_export_labels_match_frontend.py` | 导出的 CSV 里是 `MALE`、`FOLLOWING` |
| 枚举列**按什么顺序排** | `e2e/app.spec.ts` 的排序用例 | 中文对了、顺序错了，**且错得看不出来** |

**第二面是不看 payload 看像素的**：按角色走完全部页面，
断言正文里不出现任何一个必须被翻译的编码（用 `\b(CODE|CODE|…)\b` 匹配）。
词边界是有意的：`_` 属于 `\w`，所以 `\bSTUDENT\b` 不会误伤 `STUDENT_PSYCH_DETAIL`。

**第三面存在的理由**：后端 import 不了 `.ts`，所以
`services/export_labels.py` 是 `labels.ts` 里那五张表的**一份镜像**，
而 `test_export_labels_match_frontend.py` **把那份 TypeScript 当数据源读进来**逐字比对。
**改中文要同时改两边。**

**第四面是 2026-09-17 补的，也是最隐蔽的一面**：

`DataTable` 的默认排序拿 `row[column.key]` 去 `localeCompare`，
所以「关注等级」升序拿到的是 `GENERAL_RANGE` / `KEY_ATTENTION` / `NEEDS_ATTENTION`
的**字母序**，显示成「一般观察 → 重点关注 → 需要关注」。
**那看起来只是个正常的升序，没人会怀疑它错了。**

判据是 `Column.order`（`DataTable.vue`）：可排序的枚举列**必须显式声明**，
值传 `labels.ts` 的 `*_ORDER`。空值与认不出的码排在**最后，两个方向都是**。

**两处同类的按码序没修，是有意的：**

- **审计页的「角色」列**：那一张表是**服务端排序**，`ORDER BY actor_role`
  排的是编码，`Column.order` 到不了那里。要修得在 SQL 里加 `CASE` 表达式。
- ~~`ScalePage.vue` 的 `SCALE_STATUS_LABELS` 抄了一份~~ —— 2026-09-17 已删，
  改用 `labels.ts` 的 `scaleStatusLabel` / `scaleStatusTone`。
  那张表一直在 `labels.ts` 里，只是**没有取用它的函数**，视图于是自己抄了一份。
  这是第一面的反面：**表在 `labels.ts` 里而没人从那儿取，也算没接上。**

#### 7.4.3 「高度关注」不是第二个等级名，是一个功能名

**等级只有一套中文：`KEY_ATTENTION` 一律叫「重点关注」。**
但那个导出功能在按钮、弹层标题、后端错误文案与**审计动作码**
（`导出高度关注摘要`）里都叫「高度关注导出」，于是同一个屏幕上这两套字并存。

**不改名的理由**：审计动作码是**已经落库的历史**，
用户在审计页按眼睛看到的名字搜（`GET /audit-logs` 的 `q` 匹配的是 `action`）。
把界面上的名字改掉、审计码不动，正好落进"把看不懂换成了搜不到，更糟"那条教训。

**处置是在用户将要动手的那一处写出等号**：三个导出入口
（工作台、重点学生、数据中心）都有一行
「「高度关注」就是关注等级里的**重点关注**（同一档）」。**新增导出入口时照样补这一行。**

| `.metric[role="button"]` 才有手型光标 | 同上 | 判据是 `role="button"` |
| `role="status"` + `aria-live="polite"` + `aria-atomic="false"` 挂 toast **容器**上 | `Toast.vue` | 活动区域必须在内容出现**之前**就在 DOM 里；`aria-atomic="false"` 让新增的那条自己播报 |
| 登录页角色页签 `aria-pressed` | `LoginPage.vue` | 读屏软件不知道当前选的是哪一个 |
| 表单控件有 `label` | 全站 | "当前密码/新密码/确认新密码"三个框读出来一样 |
| `meta.title` → `document.title` | `main.ts` 的 `router.afterEach` | 标签页、书签、历史记录全是同一个名字 |

**这些断言的是属性与计算值，不是文案**——整块样式或某个属性被静默丢掉时会红，
而这类破坏在文本断言下是全绿的。

**「弹窗开着切页，滚动锁不留给下一页」用的是 `page.evaluate(() => window.history.back())`**：
**只有客户端路由（popstate）才会在弹窗开着的情况下把组件卸载**，
而这正是 `onUnmounted(deactivate)` 唯一从界面上可达的触发路径——
点导航被遮罩挡住，`page.goto` 是整页刷新、`body.style` 本来就会被重置。

### 7.6 答题页的四条专属约定

`StudentAssessmentPage.vue` 是**唯一一个学生会长时间停留、且答错的代价由他自己承担**的页面，
所以它有四条与其他页面不同的约定：

**① 题号只定义一次**（`questionNos`，来自 `getSessionQuestions`）。
进度、导航、「定位未答」、「答满了没有」、预计时长**全部从它派生**，不写死 100。

此前 100 在这个文件里出现六次，题库换成非 100 题的版本时两处会坏：
题**少**于一版时，学生翻过最后一题会看到「第 61 题（题干未加载…）」这种占位卡，
而提交门是"答满 100"——**永远凑不齐、交不出去**；题**多**于一版时
`next()` 停在第 100 题，后面几道走不到。

**服务端的判据是规则版本的 `question_count`，与这里回答的是两个不同的问题，别只改一边。**

**② 题干拉不到就没有答题页。** 此前是
`try { … } catch { questions.value = {} }`——拉不到题干就退化成占位卡，
而**作答与提交照旧可用**：学生可以对着一串「第 N 题（题干未加载）」
选完一整份「是」，交出一份每道题都不知道在问什么、却与真实作答在库里长得一模一样的答卷，
事后没有任何办法分辨。现在拉不到就只有一条错误与一个「重试」。

**③ 光标按会话存**，键是 `xlp_assessment_cursor:<sessionId>`；
答案一律以服务端为准，本地不留副本。

旧的全局键 `xlp_assessment_state` 里有**上一个人的答案**（机房是共用电脑，
注释还写着"服务端是事实来源"而代码是本地覆盖服务端），
所以任何学生打开这一页都**删掉**它，不是把它迁移过来。
交卷成功后连自己的光标键一起清掉。

**④ "回到哪一题"的次序**：本地光标 → 服务端的 `current_question_no`
（它本来就是"第一道未答题"，此前没有任何读者）→ 最后一题（那里才有「提交测评」）。
**从第一题重新翻一遍不是"继续答题"。**

### 7.7 失败、空态与竞态：三件事必须长得不一样

#### 7.7.1 空态是一句关于数据的话

「暂无完成明细」回答的是"这里确实只有这么多"，所以它**不能**在一次读取失败时落下。
全站统一走 `ErrorState`（带「重试」），且错误分支要**排在**空表行之前
（`v-else-if` 的次序就是这条约定）。同一页上「正在加载」与「加载失败」也必须分开：
`SkeletonBlock` 与 `ErrorState` 各自成支。

2026-09-17 修了三处：任务完成明细（此前失败只飘一条 toast、表格照样说「暂无完成明细」）、
档案详情的副面板、以及若干 `error` 与空态同屏的地方。

**toast 一飘而过，而留下的那句话会一直回答用户的问题**——
两者说同一件事时，说错的那一句是留在屏幕上的那一句。

#### 7.7.2 一次失败的读取不许留下上一次的答案

换一个版本 / 切换学生 / 重新搜索之后，面板上任何一处都不该再留着上一个对象的数据——
否则标题写着 B、正文是 A。

做法是**取数之前先清空**（`ScaleRulePanel.load`、`CareCaseDetailPage`、`CasesPage`、
`useDataImport` 的三个预览），而不是等成功再覆盖。

导入预览还多一层：留着的那份预览带着**上一个文件**的 `preview_token`
（测评导入的 token 还把"批次名称 / 测评日期"烤了进去），**拿它去提交是拿 A 的凭据交 B**。

#### 7.7.3 竞态：只有最后一次请求的答案算数

`services/latest-request.ts`，26 行：

```ts
export function createLatestRequest() {
  let counter = 0
  return {
    begin: () => ++counter,
    isCurrent: (token: number) => token === counter,
  }
}
```

**防抖不撤销已经发出的请求**——输入「张」停手 300ms 以上再补成「张三」，
两条请求都在路上，而它们回答的是两个不同的问题。

守卫用 `begin()` 取号、`isCurrent(token)` 判定，
**`catch` 与 `finally` 里也要判**：迟到的请求不能替后来者把 `loading` 关掉。

已接的三处都是"同一次停留里用户能连着发起两次"的读：审计页搜索、评分规则面板、
任务完成明细。

**两处没接，是有意的**：`CasesPage.load` 与 `CareCaseDetailPage.load`
的重入只发生在一次真实写入之后（批量分配 / 关闭档案），
而 e2e 上造那次写入会改动共享演示数据的统计口径，所以它们进不了 e2e，
也就没有可证伪的守卫——**别为它们补一个测不到的抽象**。

**竞态守卫是按页构造的**（`const latest = createLatestRequest()` 跟在
`searchTimer` 那一类状态旁边），不做成带生命周期的 composable：
一个模块级/全局的序号会把两个不相干的页面串进同一条序列，那正是这里要防的东西。

### 7.8 输入框只有两种形状，`.actions` 不是 flex 行

2026-09-17 修的一处："测评任务 → 查看明细 时，里面的输入框样式不统一"。

| 形状 | 在哪 | 长相 |
|---|---|---|
| `.search-box > input` | 搜索 / 筛选框 | 40px 高、10px 圆角、`1px solid #c8d3df` |
| `.field input` | 弹窗里的表单字段 | 100% 宽、9px 圆角 |
| **裸 `<input>`** | 「查看明细」那个筛选框此前就是这样 | **浏览器默认**：28px 高、`2px inset rgb(118,118,118)`、`border-radius: 0` |

全站只有 `button, input { font: inherit }` 这一条，**没有任何一条给裸 `input` 上色**。
所以一个不落在上面两处的输入框不会"差一点"，它是另一个物种：
灰色的凹陷直角框，挨着旁边 34px 的按钮。

**加输入框时先问它属于哪一种**，不要为它现写一套 inline 样式。

同一个元素上还有第二个空转：外层写的是
`class="actions" style="justify-content:space-between"`，
而 **`.actions` 没有基础规则**——它只在 `.page-head .actions`
（那条还在 768px 的媒体查询里）与 `.question-foot .actions` 两个限定选择器下存在。
于是 `justify-content` 从来没有生效过。**全站那个 flex 行叫 `.toolbar`**
（`display:flex; align-items:center; gap:9px; flex-wrap:wrap`）。

**其余十几处 `class="actions"` 没动**：它们要么在 `.page-head` 里（那里是 flex 行），
要么是 `justify-content:center` 而无效果（居中变成靠左，肉眼几乎看不出来）。
**没有给 `.actions` 补一条基础规则**去一次修好全部——那会同时改动十几个页面的按钮间距。

守卫用 `getComputedStyle` 断言边框是 `solid`（裸 input 的默认是 `inset`）、
圆角不是 `0px`、且父元素是 `.search-box`。
**不写死 40px / 10px**：断言的是"它属于全站那一套"，而不是"它刚好是这一版的尺寸"。

装不了 Docker，装的人不是技术人员。** 要求是拷个 zip 过去、解压、双击一下、
数据库连接在装的时候输入。

### 8.1 包的形状

zip 从 22MB 降到 11MB。

### 8.2 安装的六个步骤与三个维度

安装时要回答**三个维度**，它们互相独立：

| 维度 | 取值 | 决定什么 |
|---|---|---|
| **用法** `usage` | `single` 单机 / `lan` 局域网 | 监听地址、安装目录、要不要提权/计划任务/防火墙 |
| **数据库由谁准备** `database_mode` | `installer` / `prepared` / `schema_prepared` | 建库、灌基础数据、设管理员密码归谁 |
| **是否首次** | 首次 / 升级 | 沿用上次的用法；升级不动密码、不动 `.env` 里改过的值 |

**六步**：

```
第 1 步  问用法、问安装目录、问端口、问数据库连接、问管理员密码
第 2 步  复制程序文件（robocopy）
第 3 步  写配置（首次整份写 .env；升级只补坏行）
第 4 步  建库 / 安装依赖 / 迁移 / 种基线
第 5 步  注册计划任务 / 防火墙（仅 lan）；记 runtime\build.json
第 6 步  启动服务 + 健康检查 + 收尾说明
```

#### 8.2.1 用法：单机 vs 局域网

| | `single` 单机 | `lan` 局域网 |
|---|---|---|
| 监听 | `127.0.0.1` | `0.0.0.0` |
| 安装目录 | `%LOCALAPPDATA%\xinliceping` | `C:\xinliceping` |
| 提权 / UAC | **不要** | 要 |
| 计划任务 / 防火墙 | **都不做** | 都做 |
| 起停 | 双击「启动服务.bat」 | 常驻，开机自启 |

**叫"用法"（`usage`）不叫"模式"。** `install.ps1` 早就在打印
`模式：升级现有安装`，那个词已经指"首次装还是升级"。
再拿它指这一维，同一份日志里会出现两行互不相干的 `模式：`，而操作员要 `grep` 它找东西。

**提权块必须排在"定用法"之后、"问口令"之前，这个次序是逼出来的。**
用法决定要不要提权，它本来该挪进第 1 步去问；**不行**——提权重启的子进程从第 1 行重跑，
要让子进程不再问一遍就得把所有答案当参数传下去，
而 `$settings.dbPassword` 与 `$settings.adminPassword` **不能进命令行**
（任何账号都能通过 WMI `Win32_Process` 读到别的进程的命令行，环境块读不到）。

**升级沿用上次的用法，不再问。** `ops.ps1` 的 `Get-InstalledUsage` 读
`runtime\build.json` 的 `usage`，**读不到 / 字段不在 / 值认不出，一律回退 `lan`**：
那个字段是 2026-09-18 才有的，此前装的包全是局域网那一种，
回退成 `single` 会让那些服务器上的服务再也起不来，而"查看状态"还会说一切正常。

它**不叫 `Get-Usage`**——`install.ps1` 里那个 `Resolve-Usage` 回答的是
"这次要按哪种用法装"（决定），它回答的是"当初装成了哪种"（读取）。

**单机用法起一个可见的控制台窗口**（2026-09-18）。用户的心智模型是
"使用时启动，关机时停止"，那个模型里的动作是**关掉一个看得见的窗口**。
`Start-ServiceNow` 去掉了 `-WindowStyle Hidden`，并在收尾文案里写明
"屏幕上那个黑窗口就是服务本身，别关它"——**这是这次改动最容易被当成 bug 报回来的一点**
（装完凭空多一个窗口，用户会以为那是安装程序的残渣）。

**`-NoNewWindow` 仍然绝对不能加。** 它让子进程共用 `.bat` 的控制台，
`.bat` 一退出控制台就关、子进程收到 `CTRL_CLOSE` 当场死掉——
"启动服务"会变成"启动一下然后立刻停"。

**关掉窗口走的是 `CTRL_CLOSE_EVENT`，它发给挂在该控制台上的所有进程**，
壳与真解释器一起死——比 `Stop-Process` 更彻底，所以"关窗口 = 停服务"成立。
但 `Ctrl+C` 走 `CTRL_C_EVENT`，只发本进程组，而 venvlauncher 用
`CREATE_NEW_PROCESS_GROUP` 起子进程，所以给用户的说明里**只写"关窗口"**，
不承诺按 Ctrl+C 能停。

**注销也会停**（窗口属于那个登录会话）。

#### 8.2.2 数据库由谁准备：三种分工

| | 选 1 `installer`（默认） | 选 2 `prepared` | 选 3 `schema_prepared` |
|---|---|---|---|
| 建库 `app.db.create_database` | 跑（幂等） | **不跑**，换成连接自检探针 | 同选 2 |
| 表结构 | 迁移建出来 | 迁移建出来 | **校对**（`ensure_schema`） |
| 迁移 `alembic upgrade head` | 跑 | **跑** | **跑** |
| 空库检查 `app.db.check_empty` | 跑（只警告） | 不跑 | 跑（只警告） |
| 基础数据 `app.db.seed` | 跑 | **不跑** | **跑** |
| 基线清理 `reset_to_baseline` | 跑（除非 `-KeepData`） | **不跑** | 跑（除非 `-KeepData`） |
| 管理员密码 `set_admin_password` | 设成他输入的那个 | **不设，也不问** | 同选 1 |

**三种取值只差一件事：这个库里，哪几样归操作员。**

**迁移三种都跑，是这一维唯一一处刻意的"越界"**，判据是一句话：
**库与数据归操作员，表结构归这一版程序。**
不跑它的下场不是报错，是"屏幕说安装成功、页面 500"——
换了程序文件而表结构停在上一版时**登录页照样打得开**
（它读的 `system_setting` 读不到就回退 `DEFAULTS`），
而第 6 步那个健康检查探的正是登录页要的那一个端点，
所以这种"一半坏掉"它抓不住。

**默认值是 1，因为它必须回到"这一问加进来之前的行为"**：
改成 2 的话，一台全新机器上直接回车装出来的系统**打不开任何页面**
（库里没有量表、没有 admin），而屏幕上写着"安装完成"。

**选 3 逼出了 `ensure_schema`**：手写的建表语句里**没有 `alembic_version`**
（那是 Alembic 自己的版本记录表），而迁移是无条件跑的，
表已经存在时它在第一条 `ALTER TABLE … ADD COLUMN` 上撞 `Duplicate column name`。
所以迁移**之前**多一步 `python -m app.db.ensure_schema`：

| 这个库的状态 | 它做什么 |
|---|---|
| `alembic_version` 在、版本认得出来 | 什么都不做 |
| 一张应用表都没有 | 什么都不做 |
| 有表、**没有** `alembic_version`、缺表或缺列 | 退出码 1，逐条列出缺什么 |
| 有表、**没有** `alembic_version`、对得上 | `alembic.command.stamp` 补一行版本号，退出码 0 |
| 版本表**空着**、或版本号认不出 | 退出码 1，让它 `DROP TABLE alembic_version` 后重跑 |
| 版本表说 head 而表缺列 | 退出码 1（说 head 就得真的是 head） |
| 版本表比 head 旧 | 放行，并多说一句"重跑可能撞 Duplicate column" |

它**只比表名与列名，不比类型**：类型一起比要上 `compare_metadata`，
而 MySQL 的反射噪音（`tinyint(1)` vs `BOOLEAN`、server default）会把一份
本来能用的表判成不一致。**宁可漏报，不要误杀。**

**第 4 步"建库"那一处的判据写成 `-eq 'installer'` 而不是 `-eq 'prepared'`**：
三种取值下"我来建库"恰好只有一种。写成
`if prepared { 探针 } else { 建库 }` 的话，**选 3 会掉进 else 去建库**——
而选 3 的全部含义就是"库和表都建好了"。

### 8.3 `cryptography` 是**前提**，不是顺手带的

MySQL 8 默认认证插件是 `caching_sha2_password`。它在服务端**内存里**
缓存了该账号的凭据时走快路径（只做一次 SHA256 scramble，用不到 RSA，
也就不需要 `cryptography`）；缓存未命中才走 `sha2_rsa_encrypt`，
而 `pymysql/_auth.py` 在那条路上直接
`raise RuntimeError("'cryptography' package is required …")`。

**那个缓存是服务端内存里的，MySQL 一重启就空。**
所以"装的时候连得上"证明不了任何事：装完重启一次服务器，
或者换一台全新的 MySQL，应用就再也连不上库。
它写在 `deploy/requirements.lock.txt` 里，**不依赖任何人的记忆**。

### 8.4 崩溃重试在自己的循环里，不在计划任务里

**Task Scheduler 的 `RestartOnFailure` 只在"根本起不来"时触发**——
凭据错、exe 不存在、ACL 不放行。`python.exe` 起来了、跑了一半崩掉
（退出码非 0），**它不会重启**。计划任务也不参与 SCM 的依赖图，
所以 `depend= MySQL80` 这个写法不存在。

```python
while True:
    wait_for_database(settings, logger)   # 连不上就一直等，指数退避封顶 30s
    try:
        uvicorn.run(...)
    except Exception:
        time.sleep(CRASH_RETRY_SECONDS)   # 崩了就重来
        continue
    else:
        return 0                          # 正常返回 = 收到关停信号，**不重启**
```

`else` 那一支不能省：`Stop-ScheduledTask` 是硬杀，但如果进程是收到
Ctrl+C / 信号正常退出的（手工跑、调试），把它拉起来就成了"停不掉的服务"。

数据库那一层同理——开机时 MySQL 服务往往还没起来，
装的时候连得上不代表重启之后连得上。

**计划任务用 cmdlet 注册，不用静态 XML**（`New-ScheduledTaskAction` /
`-Trigger` / `-SettingsSet` / `-Principal` + `Register-ScheduledTask -Force`）。
**没有 `deploy/task.xml` 这个文件**。理由是把整类风险消掉：
静态 XML 要求元素顺序与官方 schema 完全一致，写错是**装的时候才报**，
报出来还是 schtasks 的原文；cmdlet 在注册那一刻由 PowerShell 自己校验。

三个容易漏的参数值：

- **`-ExecutionTimeLimit ([TimeSpan]::Zero)`** → `PT0S`。
  从 XML 建的任务默认是 **PT72H**，也就是装完三天后会被 Task Scheduler 掐掉——
  而它看起来一切正常。
- `-MultipleInstances IgnoreNew`：升级时旧进程还没退干净，不会起出第二个。
- `-UserId 'SYSTEM' -LogonType ServiceAccount -RunLevel Highest`：
  开机就跑，**不需要有人登录**。

### 8.5 venv 的 `Scripts\python.exe` 不是解释器，是**一个转发壳**

**这是部署这一层最有复用价值的一条。**
CPython 3.11.9 的 `Lib/venv/__init__.py:253-254`：

```python
# On Windows, we rewrite symlinks to our base python.exe into
# copies of venvlauncher.exe
basename, ext = os.path.splitext(os.path.basename(src))
```

那个壳（`PC/venvlauncher.c`）读 `pyvenv.cfg`、对**真正的**解释器
`CreateProcessW` 然后等它。于是服务在进程表里是**两个**：

```
<安装目录>\runtime\venv\Scripts\python.exe   ← 壳（venvlauncher）
        └─ <base python>\python.exe          ← 真占端口、真连库、真锁 .pyd
```

**Windows 不连坐。** 只按 `Path -eq $PythonExe` 找进程、只杀外壳，服务一点没停。
三条后果全是静默的：

1. `venv --clear` 删不掉被孤儿映射着的 `.pyd`（`PermissionError`，**每次升级都撞**）；
2. 第 6 步 `Start-ServiceNow` 看不见孤儿 → 起出第二个 → 第二个绑不上端口而
   `run_server.py` 的 `while True` 每 30 秒重试一次 →
   `Wait-ForHealth` 拿**旧进程**的应答报"安装完成"；
3. 「停止服务.bat」杀完壳端口还在应答。

所以 `install.ps1` 与 `ops.ps1` 的 `Get-ServiceProcess` **都改成收整棵进程树**
（按 `ExecutablePath` 认根，再按 `ParentProcessId` 收直接子进程）。
**两处必须都改**：`ops.ps1` 那一份用的是不带 `$script:` 前缀的 `$PythonExe`，
是两处独立编辑，不是复制粘贴。

**没有用 `taskkill /F /T`**：那会经 `Invoke-Native`，把"原生调用点恰好三处"
那条守卫撞坏；而 `taskkill` 找不到进程返回 **128**，在这里是正常情况。

### 8.6 运维：八个按钮 + 两枚手工按钮

`ops/*.bat`（装完由 `install.ps1` 拷到安装根目录再删掉源目录）：
启动服务 / 停止服务 / 重启服务 / 查看状态 / 查看日志 / 备份数据 /
重置管理员密码 / 卸载。

**两枚手工按钮**（`手工启动后端.bat` / `手工启动前端.bat`）
补的是**"装不下去"这个场景，不是第二种装法**。
不注册计划任务、不放行防火墙、不设管理员密码、**不写 `runtime\build.json`**——
所以「查看状态.bat」对它们开出来的服务一无所知。
它们做的是"把 `install.ps1` 第 2～4 步那几件事补上、并当场把服务跑起来"。

**它们留在 `deploy\` 里，不进包根**：摆在包根会让一个还没开始装的人
先看到两个"手工"按钮，而他此刻该点的是「一键安装.bat」。

**清库要先问人**（`Read-Host`，回车那一支是"不清"）：
`install.ps1` 里 `reset_to_baseline --yes` 是无条件跑的（那条路上整件事都在安装器手里），
而手工这条路不假设任何东西。**一个破坏性动作的默认值不能是破坏。**

### 8.7 编码：这套资产里最容易踩的一处

Windows 侧那几个文件在开发机上一行都不会执行，第一次被执行是在一所学校的服务器上。

| 文件 | 约定 | 违反了会怎样 |
|---|---|---|
| `.ps1` | **必须**有 UTF-8 BOM，且**恰好一个** | PS 5.1 按 ANSI 代码页读它，中文全乱；cp936 下中文字符的尾字节还会吞掉紧跟的 ASCII 字符 |
| `.txt` | 必须有 BOM，且**恰好一个** | 记事本打开是乱码 |
| `.bat` | **不许**有 BOM，且每个字节 < 128 | BOM 把第一行 `@echo off` 读坏 |
| `requirements.lock.txt` | **不许**有 BOM，且每个字节 < 128 | 读它的是**目标机上的 pip** |

**"有个 BOM"与"只有一个 BOM"是两件事。**
`install.ps1` 的开头一度堆着**四个** BOM，而当时**两条守卫都报绿**——
两条都只查 `startswith(BOM)`。守卫是
`test_the_bom_is_exactly_one_and_nowhere_else`：开头**恰好**一个，
且全文除它以外**一个 U+FEFF 都没有**。

**pip 按 locale 编码读 `requirements.lock.txt`，所以那个文件必须纯 ASCII。**
`pip/_internal/req/req_file.py` 的 `get_file_content()` 把**整个文件**交给
`auto_decode()`，而它在文件没有 BOM 时退回 `data.decode()`，
也就是**当前 locale 的编码**。中文 Windows 上是 GBK，
所以这个文件里**任何一个中文字符**都会让 pip 当场抛
`UnicodeDecodeError: 'gbk' codec can't decode byte 0x84 in position 16`
——**注释里的也算**。

**判据不是"用某个 locale 解一次能过"，是逐字节 < 128**：
一个 GBK 双字节序列（`C4 E3`，就是"你"）在 cp1252 下也是合法输入，
两边各自解出**不同的**乱码。

代价是这**一个**文件的注释只能用英文（唯一一个这样的文件）。

**原生工具的输出是另一套编码**：robocopy / icacls 这类工具
**重定向到文件时写的是控制台代码页**（中文 Windows = cp936），
只有直接挂在控制台上的 `WriteConsoleW` 那条路才是宽字符。
归 `Read-NativeOutput`（`[Console]::OutputEncoding.GetString`，**只读不改**）。
**Python 子进程那一路保持不变**（`sitecustomize.py` 把它的 stdout 固定成 UTF-8）。

### 8.8 外部命令的退出码要逐个工具判

**`robocopy` 的退出码是位掩码**，不是 0 / 非 0：

| 码 | 含义 |
|---|---|
| `0` | 目标已经是最新的，没东西可拷 |
| `1` | **成功复制了文件** —— 全新安装必然是这个 |
| `2` | 目标目录里有多余文件（刻意不加 `/MIR`，所以是正常现象） |
| `3..7` | 上面那些的组合 |
| `8` | 有文件没能复制（重试次数用尽，多半是文件被占用） |
| `16` | 严重错误，一个文件都没复制 |

`Invoke-Native` 收一个**声明出来的**成功码表 `[int[]]$SuccessExitCodes = @(0)`，
robocopy 那一处显式传 `(0..7)`。

**"跑外部命令并判成败"这件事在仓库里有三处实现，各判各的**，
所以别假设对了的那一处能证明另外两处。

### 8.9 PowerShell 的"空"有三种

| 写法 | 拿到什么 |
|---|---|
| `$x = @()` | 空数组，`.Count` 是 `0` |
| `function f { return @() }; $x = f` | **`$null`**——空数组在管道里被**拆没**了 |
| `$x.Count`（`$x` 是 `$null`） | 正常模式下是 `0`；`Set-StrictMode -Version Latest` 下**抛异常** |

`Get-LanAddresses` 用 `return @($addresses)` 收尾，而 `Get-NetIPAddress`
在那台机器上一个匹配的地址都没返回，于是 `@()` 变成 `$null`，
`$lanAddresses.Count` 当场抛——**在六步全过、健康检查回了 200 之后**，
操作员看到的最后一句是"安装没有完成"，而那时服务已经在跑。

处置两半：调用点写成 `@(Get-LanAddresses)`，并且**一个私网地址都没有时照样把地址给出来**
（只排掉环回与 `169.254.*`）——那句"老师这样访问："存在的全部意义
就是给操作员一条能念给同事的地址。

**严格模式下"读取"不存在的属性就抛异常，转型挡不住。**
`$settings.dbUser` 在升级路径上不存在（那一支只返回 3 项），
而 `[string]$Settings.dbUser` 的转型**排在读取之后**——一个都挡不住它。
判据是**"键在不在"**（`Get-SettingText` 用 `ContainsKey`），
不是"值空不空"（那会把 `XLP_PORT=0` 这种合法的值一起当成缺项）。

### 8.10 升级：不动管理员密码，不动 `.env` 里改过的值，不用人先去停服务

**升级（`Read-InstallSettings -Upgrade $true`）根本不问也不设管理员密码。**
"重新装一遍"既不会要你再输一次，也不会把你改过的那个冲掉。
**升级只做两件事：更新程序文件 + 跑一次迁移。**

**升级就地补 `.env`，不整份重写**：`XLP_HOST=127.0.0.1` 是操作员
在局域网用法上**刻意**改的，重写它等于把"只有本机能访问"悄悄改回"整个网段都能访问"。
"升级不动它"这句承诺的正确读法是"**不改你改过的值**"，不是"不看你写的那几行"。

**升级不用人先去停服务**——安装程序自己会停，而且**它必须自动停，因为不停就装不上**：
正在跑的那个 `python.exe` 锁着 venv 里的 `python*.dll` 与 site-packages 里的 `.pyd`
（而且锁住它们的是子进程，见 §8.5），第 2 步的 robocopy 会复制到一半失败（退出码 8）。
**这一条不是体贴，是前提。**

**忘了密码的出路是安装目录里的「重置管理员密码.bat」** →
`ops.ps1 -Action reset-admin` → `python -m app.db.set_admin_password`。
**不需要重装、不需要 mysql 客户端**——界面上的改密码要求本人先登录，
所以第一任管理员的密码一丢，这个部署就进不去了。

**收尾文案里的按钮名必须与磁盘上的文件名一字不差。**
那句话原本写的是"改管理员密码"，而磁盘上那个文件叫「重置管理员密码.bat」——
**它是整段话里唯一一处告诉操作员"忘了密码怎么办"的地方**。

### 8.11 卸载不删数据，停用立即生效

`ops.ps1 -Action uninstall` 删的是计划任务、防火墙规则、程序文件；
**数据库里的东西一行不碰**，并且在界面上明说。
删掉 `user_account` 那一行会让 `audit_logs` / `manual_review` 全部悬空，
而安装目录与数据库本来就是两件可以分开处置的东西。

### 8.12 这套东西**没有**做的事

- **没有 TLS。** 局域网用法只给局域网用；单机用法压根不出这台机器。
  直接暴露到互联网需要另外配 HTTPS。
- **没有"单机 → 局域网"的在线切换**，只做卸载重装。
- **局域网用法下「备份数据.bat」对普通用户是失效的**（它要读只授了
  SYSTEM 与 Administrators 的 `backend\.env`）。现在的处置是在错误信息里
  **把两种原因分开说**（权限 → 以管理员身份重试；文件坏了 → 去改）。
- **没有多校。** 学生导入链路仍然硬编码 `School.code == "QH"`。
- **备份不自动上传。** 只在本机落一份 `.sql`，脚本顺手删 30 天前的旧文件，
  所以"一直没拷"的下场是**什么都没有**。
- **没有自动放行杀毒软件。** 包里没有未签名的 `python.exe` 了，
  风险从"包里带了什么"移到"装的过程做了什么"。**没有**用 `Add-MpPreference`
  静默地把整个目录加进排除项：以 SYSTEM 身份削弱一台学校服务器的杀毒软件
  是**对外生效且难以回退**的动作，不该由安装脚本替操作员决定。

### 9.1 规模

| 前端 e2e | **113** 个测试（`app.spec.ts` 104 + `vocabulary.spec.ts` 9） | `make e2e` | 两个服务 + `seed-demo` |

### 9.2 后端测试：内存 sqlite + metadata 建表

`tests/conftest.py`：

```python
@pytest.fixture
def db_session():
    engine = create_engine("sqlite://", connect_args={"check_same_thread": False},
                           poolclass=StaticPool)
    Base.metadata.create_all(engine)
    ...  # 用 seed_development_data 种基线
```

**三个后果，每一个都要理解：**

1. **完全不跑 Alembic。** 模型与迁移的漂移不会被测试发现（§5.6.1 就是它的一个实例）。
2. **外键默认不检查。** 父行先删在 sqlite 上照样全绿，在 MySQL 上是必然的 1451。
3. **schema 是 metadata 那一套**，不是迁移那一套——20 列 `server_default` 不存在。

**凡是要验证"只有真库才会报"的东西，必须自建引擎并开约束**：

```python
# tests/test_purge_demo.py
engine = create_engine(...)
@event.listens_for(engine, "connect")
def _fk_pragma(dbapi_conn, _):
    dbapi_conn.execute("PRAGMA foreign_keys=ON")
```

**pragma 在事务里是空操作，必须"在连接建立时"设。**

`test_sql_reset_to_baseline.py` 走得更远：它**不需要数据库**，
按 `Base.metadata` 的外键图把 SQL 脚本的删除顺序重推一遍——
所以那条守卫在 sqlite 上也是有效的，把"只有真库会报"的缺口补上了一块。

**种子数据**从 `db/seed.py` 起步（青禾实验学校 / 初一 / 1 班 / `S001` 林同学 /
`MHT-1.1.0` / `TASK-2026-FALL-MHT`）。量表版本由 `seed.MHT_SCALE_VERSION` 一处决定。

### 9.3 e2e：只看像素与计算值

`e2e/app.spec.ts` 25 个 describe 组（104 个用例）+ `vocabulary.spec.ts` 1 组（9 个）。

**依赖 `seed_demo.py` 的演示数据**，所以**跑 e2e 之前必须先 `make seed-demo`**。
`make purge-demo` 之后不补这一步会有一批用例因为"没有数据"而失败——
**这些是数据量依赖，不是回归**。正确处理是补数据，不是把断言改松
（改松会把分页/复测的覆盖一起丢掉）。

**e2e 的三条设计原则：**

**① 断言计算值而非文案。** 「布局完整性」与「无障碍契约」两组读的是
`getComputedStyle` / `aria-sort` / `aria-pressed` / `role=status` /
`document.body.style.overflow`——曾捕获过一次"整块组件规则被静默丢弃
但所有文本断言仍然通过"的故障。

**② 数行数要问接口要，不要写死。** 「全部学生」用例断言的是
"列表的条数与名册的行数相等"（`共 N 条` 对 `GET /students` 的 `items.length`），
而不是"28 名学生"。**同一个道理也管界面上的品牌文案**：
校名、品牌名、副标题都是操作员可配的，断言它们的地方一律从 `/public/branding` 现取。

**例外是「系统配置」那一组内部的两处 `toHaveValue('青禾实验学校')`**：
那一组自己把配置重置到了出厂值，它断言的正是"出厂值是这一个"——
那不是数据依赖，是那条用例的主题。

**③ 先证明有东西可扫，再断言它干净。** 这条在四个地方出现过：
档案弹层在"正在加载明细"那一帧就被扫描（明细表还一行没渲染）；
`/counselor/cases/1` 没有复测计划（页签里的 `v-for` 空转）；
「全部学生」页签切过去才请求数据（扫到的是骨架屏那一帧）；
审计页竞态那条必须先断言"共 22 条"再断言"慢的答案"不出现。

### 9.4 一个反复出现的教训：**别为了用例的起点去改数据**

**跑 e2e 不许改掉操作员自己配的东西。** 「系统配置」那一组此前的
`beforeEach` / `afterEach` 都调 `/admin/settings/org/reset`，
于是**每一次全量 e2e 都把 `org` 这一组恢复成出厂值**。
在一台有人用过的机器上，"恢复成出厂值"与"恢复成原样"差着一整份配置。

现在这一组在 `beforeEach` 里**先读一份快照**再重置，
`afterEach` 按原样 `PUT` 回去。两个细节都不能省：
**快照只读一次**（某条用例红在半路时，重读会把这次用例的残留记成"操作员的原值"），
**管理员 token 一起存进快照**（`afterEach` 跑在用例留下的那个 token 上，
而"心理老师进不去配置页"那条留下的是心理老师的，`PUT` 会 403 而静默失败）。

**学生导入的冲突面板 e2e 只跑「放弃」那一支**：
共享的开发库里 `S001` 是种子名册上的林同学，选「覆盖」会把他挪出种子里的班，
跑一次就让**别的**用例看到另一份名册。**不靠改断言，靠不碰数据。**

**唯一已知且接受的残留**：「账号管理 → 新建账号」那条每跑一次
就留下一个停用的临时账号（账号是时间戳所以不会撞），
而账号**没有删除接口**。它看得见、点得掉、不影响别的用例。

### 9.5 数据范围：老测试对它是**零信号**

`conftest.py` 只种一所学校 / 一个年级 / 一个班 / 一个学生，
且每个账号的 scope 行都覆盖全部，所以**任何范围谓词——写对、写反、还是不写——
老测试全绿**。

验证数据范围只能靠 `tests/test_data_scope.py`，它自建第二所学校（云海中学）。
**改这一块时请照同样的办法验证：临时把入口改成空操作，确认新测试会变红**，
否则测试是摆设。两个入口都要各验一次：

| 变异 | 结果 |
|---|---|
| 把守卫 `ensure_student_in_scope` 改成空操作 | 12 红 / 7 绿 |
| 把谓词 `student_scope_predicate` 改成恒真 | 23 红 / 8 绿 |

**第二所学校的学生必须带上全链路记录**（任务目标、会话、结果、维度结果、
风险事件、档案、跟进、复测、审计），否则"列表里没有他"这条断言
会因为没有他而通过，**测试白写**。

**日期用相对今天算**，提醒与复测面板只看固定窗口，写死日期会让测试自己过期。

### 9.6 变异验证：每一条守卫都要能变红

这是本项目测试文化里最强的一条。**每加一条守卫，都要实际把它破坏一次、确认它变红。**

几个实测记录：

| 守卫 | 变异 | 结果 |
|---|---|---|
| `e2e` 枚举列排序 | 摘掉那一列的 `order` | 红 |
| 同上 | 把 `DataTable` 里的 `order` 分支改成恒假 | 红 |
| BOM 恰好一个 | 多一个 / 四个 / 正文夹一个 / `.txt` 少一个 | 4/4 红 |
| `database_mode` 分支 | 20 条断言 | **20/20 红** |
| `Get-SettingText` | 裸赋值回来 / 新加没人赋值的 `.Count` / 守卫正则坏掉 | 7/7 红 |
| 收尾说明不能报失败 | 整对 `try/catch` 删掉 / catch 改回那句 | 4/4 红 |
| 包内 `.bat` 名存在 | 写一个不存在的名字 / 后缀匹配改成相等 | 5/5 红 |

**变异验证本身也会踩坑，两条值得记：**

**① 复原校验必须拿"落盘的原始字节"当基准。** 一次变异验证把基准读成
`read_bytes().decode("utf-8")`——**少了 `-sig`**。于是 U+FEFF 留在了字符串里，
复原时又写了一遍 `BOM + 文本`：跑一次多一个，那个脚本跑了三次就是四个 BOM。
而它自己的"复原 ✅"是绿的，因为那一句比的是**内存里那一份基准**，
而基准本身已经带上了 U+FEFF——**拿嫌疑人的证词给嫌疑人作证**。

**② 判据写成"整份清单里出现过这几个字"，就只能证明"有人说过这句话"。**
一次断言两个 BOM 的检查被"另一个文件满足条件"顺手满足了，
改成**按文件找**（`one.startswith(name)`）之后才红。
另一处：手册里那一节改个名，守卫仍然是绿的——因为那一节别处还有两处
**指向它**的交叉引用，按"出现过"断言的话，把标题改掉而引用留着照样绿。

### 9.7 PowerShell 资产怎么自证没写坏

`install.ps1` 与 `ops.ps1` 在开发机上一行都不会执行（本机没有 PowerShell），
所以 `test_windows_assets.py` 是**读它的正文**做文本断言。
但文本断言有个盲区：**看不见块结构**。一次手改漏了一个 `}`，
而上面那批逐字断言一条都没红。

**能用的办法是"括号差分"**：拿上一版**已经装成功过**的那一份当基准，
逐行 `difflib.unified_diff`，断言

- `{` 与 `}` 的增量**相等**；
- 新增行减删除行的**净 `{` 数 = 0**。

**两条都不用懂 PowerShell 的词法**，所以不会自己跟自己打架——
它只要求"这一版的括号形状与那一版相同"，而那一版写过一次真机日志。
基准要取**包里的那一份**，不是"我记得改之前是什么样"。

**这条办法有前提**：手上得有一个跑通过的旧版本。
第一次改这个文件的人没有，所以它不能替代逐字读一遍。

**2026-09-18 补：剥壳器修好之后它是能用的。** 之前两版剥壳器给出互相矛盾的
数字（`195/195` vs `238/237`），病因是：**here-string 的收尾 `'@` 后面可以有代码**。
这份文件里恰好有一处：

```
            $configProbeCode = Invoke-PythonScript '配置自检' 'config' @'
…正文…
'@ -Arguments @($settings.dbUser, …) -AllowFailure
```

凡是把"收尾标记 = 整行"当判据的剥壳器都会**从这里开始一直留在 here-string 里面**，
把后面所有真代码当成正文吞掉——这一吞让括号计数凭空多出 `+1`，
而 `+1` 看起来**正好像"漏了一个 `}`"**，也就是这条检查唯一要抓的那个形状。

修好之后（收尾行按 `lstrip().startswith("'@")` 判、余下那段接着当代码算，
另加 `<# #>` 块注释的进出）：`install.ps1` 2516 行、`ops.ps1` 746 行，
**两份的收尾深度都是 0**。

**它的盲区要一起记住**：只能发现"总数对不上"与"提前闭合"，
**净零的错位看不见**（在 A 处删一个 `}`、在 B 处多一个 `{`，两侧抵消而中间那段全乱）。
所以它是**一次诊断，不是一条守卫**——它不该进 `test_windows_assets.py`：
一个半吊子词法器在那里出错是无声的，而**判错一次就不再有人信它**。

## 10. 已实测的偏差与技术债

### 10.1 缺陷（有名字、有位置、有理由未修）

#### T-01 `GET /audit-logs` 不发 `detail`，所以"已记录"与"可追溯"之间有差距

**现象**：`api/v1/audit.py` 的序列化只发
`id` / `action` / `resource_type` / `resource_id` / `actor` / `purpose` / `created_at`，
**没有 `detail`**。审计页也不渲染它。

**后果**：以下内容**全部写进了库，没有任何接口或界面能读出来**——

- 导出的**遮蔽模式**（实名 vs 遮蔽）——而这一项的存在理由正是
  "同样的 action、同样的 resource_type、同样的 purpose，遮蔽与实名两条行长得一模一样，
  轨迹就答不上『这份文件是不是实名的』"；
- 导入的 `created` / `updated` / `skipped` 与 `resolution`；
- 年龄覆盖的旧值与新值。

**为什么不顺手加**：要给 `/audit-logs` 加一个 `detail` 字段，
并想清楚它该不该受权限约束——同一张表里既有"登录失败"也有"查看了谁的档案"。
**这是一个需要决定的改动，不是一个补字段的改动。**

#### T-02 审计页的搜索提示与后端行为对不上，且 `resource_type` 是裸编码

- `AuditPage.vue` 的搜索框写着「搜索行为、对象或用途」，
  但服务端 `q` **只匹配** `action` / `resource_type` / `resource_id` 三个**编码**，
  `purpose` 根本不参与匹配；
- `AuditPage.vue` 直接把 `{{ row.resource_type }}` 渲染成
  `EXPORT` / `RISK_EVENT` / `USER_ACCOUNT`。

**2026-09-16 曾给这一列加中文映射，随后撤回**：文案一改，
用户照着提示输入「关注档案」会一条都搜不到，
**把"看不懂"换成了"搜不到"，更糟**。

**正确的修法是三件事一起做**：① 先加服务端 `resource_type` 筛选器
（枚举下拉，与 `actor_role` 并列）；② 再把展示改成中文；
③ 最后把提示语改成与 `q` 实际匹配的字段一致。

#### T-03 `ScalePage.vue` 的发布按钮是死代码

`ConfirmDialog` 在 `ScalePage.vue:7` 被 import，但**模板里从未渲染它**；
`publishScaleVersion` 有且只有一个调用者（`ScalePage.vue:87` 的 `confirmPublish()`）——
而那个函数没有任何东西会触发。**从界面上发布一个草稿量表走不通。**

后端 `POST /scales/versions/{id}/publish` 是好的、有测试的，
所以这是纯前端缺口。它和 §7.2 那条是同一个形状：
**死在 `v-if` 里（或者说，死在一个没人挂的处理器里）的东西，
两个 e2e 角色用例都不会发现。**

#### T-04 revision id ≤ 32 字符这条规则**没有任何测试把守**

它写在**每一条迁移的 docstring 里**，而 `test_*` 里没有一条检查它。
当前最长 29 字符（`0009_student_profile_duration`），余量 3 个字符。
`__pycache__` 里还留着一条 33 字符的旧 `.pyc`（`0009_student_profile_and_duration`），
说明这条规则**正在被踩**。

**这条守卫很容易写**（遍历 `versions/*.py` 提取 `revision`，断言 `len <= 32`），
而且它是那种"不写就一定会再犯"的规则——因为违反时**不会报错**，
只在下次 `upgrade` 时撞 `Duplicate column`。

#### T-05 `api/v1/audit.py` 用硬编码 `require_role` 而不是能力矩阵

`require_role(ADMIN, COUNSELOR, LEADER)` 与 §3.6 的约定不一致。
**读审计该不该是某个能力，尚未决定**——如果它是能力，
那它应该是第六个能力（"审计查看"），而那要一次产品决定。

#### T-06 前端没有 lint / format 配置

没有 ESLint、没有 Prettier、没有 `.editorconfig` 的提交。
类型检查（`vue-tsc -b`）是唯一的静态检查。
代价是代码风格靠人维持，`labels.ts` 里那 400 行的表格式就是证据
（它是手工对齐的）。

#### T-07 `docker-compose.yml` 的 MySQL 口令与默认值不一致

`docker-compose.yml` 是 `root/root`，而 README 与 `core/config.py` 的默认值是
`root/password`。按 README 手动起 mysql 容器再本地起后端会连不上。

### 10.2 已知缺口

#### G-01 学生导入链路硬编码单校

`preview_student_import` 与 `commit_student_import` 都硬编码 `School.code == "QH"`，
测评导入的 `school_for_import` 同样。学号查重已对齐到同一所学校，
但**整个链路仍然是单校写死的**。多校部署需要先改这里。

`student` 表的 `UNIQUE (school_id, student_no)` 已经为多校留了余量，
但**用不上**。同理，`user_scope` 的 `SCHOOL` 级与
`school.name` 在界面上"从来没有出现过"这件事，都是同一个单校假设的不同侧面。

#### G-02 小范围聚合有反推风险

一个只覆盖 3 名学生的 `CLASS` 范围，维度高亮率 100% 等于点名。

**当前场景（整班、整年级）够用**，但把范围切到 `STUDENT` 级时要重新想。
2026-09-17 起**比率与均值**有了护栏（`MIN_COHORT_FOR_AGGREGATE = 5`），
但**计数仍然全量下发**（"3 人里 2 人"不给百分比，可"需关注 2 人"照给），
所以这条缺口没有真正关闭。

**同一处还有一处未加护栏的**：`dimension_distribution` 的 `high_rate`
与 `average_score`（分母是调用者范围内的**已测评人数**）。
它 2026-09-17 已收敛到 `latest_result_subquery` 同口径，但小样本那一层没有——
一个只覆盖 1 名学生的范围，那一行维度均值就是这名学生自己的分。

**没顺手补上是因为代价不划算**：三条既有测试
（`test_analytics_dimensions.py` 两条、`test_assessment_import_api.py` 一条）
正是拿"1 名学生"当最小夹具去钉别的东西，套上护栏就得先把它们的夹具扩到 5 人
并重算期望值，而那会把它们各自要钉的那一点冲淡。**要补请单独做，并保留那三条测试的原意。**

**以及管理员自身也受 scope 约束**：seed 给 admin 的是 `SCHOOL/青禾`，
所以多校部署时管理员只会看到青禾的学生。**管理员的 scope 该怎么配是个未决的产品问题。**

#### G-03 导入会改统计口径

`source=IMPORTED` 按系统内作答同一口径判定，但仍然会改口径：

| 会被改的 | 怎么改 |
|---|---|
| `analytics_service` 的完成率 | **不按任务过滤** → 批次任务的目标行计入完成率 |
| `attention_count` / `attention_rate` | 取**每人最近一场** → 导入那一场若比校内那一场新，这个学生的等级就来自外部平台，直接进关注率 |
| `export_service` 的 `high_risk_only` 与「来源」列 | 取**每个学生最新一场会话** |
| `analytics_service.leader_progress` | 同受此影响 |

**这是导入功能的固有性质，不是缺陷**——"来源"列就是为此加的。
要记住的是：**导入一批校外普查之后，学校的关注率与完成率都会变**，
而这是设计意图。

#### G-04 健康检查探的是"服务起没起来"，不是"库全不全"

一个只灌了一半的库（有 admin 没量表）照样返回 200，
因为登录页要读的 `system_setting` 读不到会回退 `DEFAULTS`（§3.3）。
这是"配置读不到就回退默认值"这条 fail-safe 的**副作用**：
它在别处是"不许 fail-open 成空界面"，在这里恰好让一个空库看起来是好的。

`check_empty` 把这条缺口收窄了一半（它就是在读表），
但**它回答的是"有没有数据"，不是"数据全不全"**。

**真要做成"量表在不在"的探针，得指名去查那张表**，
而它属于"选 2 那条路"（数据归操作员），那是另一件事。

#### G-05 前端没有路由守卫

`main.ts` 无 `beforeEach`。角色门禁靠 `AppLayout.vue` 拿到 `/auth/me` 后
比对 `meta.role`，不匹配就 `router.push('/login')`——越权访问表现为"被弹回登录页"。

**后端鉴权是最终权限来源，前端隐藏不是安全措施。**
但这条设计有一个真实代价：**一个角色的页面永远到不了这件事，
没有任何测试会发现**（§7.2）。

#### G-06 移动端覆盖不足

只有一个 375×667 的登录页冒烟测试。**学生答题页在手机上是真实场景**，
当前没有覆盖。而 `StudentAssessmentPage.vue` 恰恰是全站交互最复杂的页面。

### 10.3 一处"看起来像 bug 但不是"的地方

**`seed_demo` 的 `display_name` 就是角色名**（"心理老师"），
所以演示库里的审计页「操作人」列会读成「心理老师 · 13800000001」。
**那是演示数据的性质，不是这一列没接上**；真实名册下它显示的是人名。

同类还有几处，都记在 `CLAUDE.md` 的测试注意里：

- `seed_demo._ensure_student_account` 会给每个演示学生建账号
  （4 个基础账号 + 27 个演示学生 = 31），所以**不要给账号表加精确行数断言**；
- 审计分页的两条"首页恰好 20 行"依赖库里有演示数据，清库后就红，
  而红的原因不是功能坏了。
